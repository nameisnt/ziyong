# 聊天备份书架与原生导入恢复 App 方案

> 历史归档：R0—R5 已实施，本文件只保留产品决定、实现边界和验收记录，不得作为当前待办或自动执行依据。当前备份规范以 `docs/05-数据备份统计与迁移.md` 和 `docs/07-当前代码与UI复用审计及设计要求.md` 为准。

## 一、状态与实施顺序

- 状态：**已完成（2026-08-11，R0—R5 已实施；R3 的暂缓项保持不变）**。
- 前置方案：`docs/archive/08-结构整改与备份安全迁移交接.md` 已全部完成并通过最终验收。
- 本方案与 08 的结构整改保持独立；恢复 App 没有反向侵入创作 App 的业务状态。
- R3 已完成首轮评估，群聊专用导入、手动选择任意 JSONL、插件 scope 复制均未混入首版，决策见本文第十四节。

## 二、目标

新增独立的“酒馆备份管理”App，将 SillyTavern 自动生成的聊天备份作为只读书库展示；内部 App ID 继续保留 `recovery`，避免破坏既有路由和用户排序：

1. 首页读取当前用户的全部 `chat_*.jsonl` 备份。
2. 首页只展示角色卡或特殊分组及其备份数量；进入角色卡后再展示该组的备份列表。
3. 用户可先阅读备份中的聊天楼层，确认内容是否正确。
4. 用户确认后，调用 SillyTavern 原生聊天导入流程，将备份导入对应角色卡。
5. 插件不直接覆盖现有聊天，不自行写入 `chats` 文件夹；只有用户明确确认单条删除或快速清理时，才调用酒馆原生备份删除接口。

这里的“导入”会由 SillyTavern 原生接口在目标角色卡下生成一份导入后的聊天 JSONL；该落盘行为属于酒馆原生导入结果，不由插件直接创建或拼装文件。

## 三、明确不做

1. 不覆盖事故聊天或任何已有聊天。
2. 不调用聊天删除接口。
3. 不绕过酒馆接口直接操作 `backups` 文件夹；删除只调用原生聊天备份删除接口。
4. 不把备份内容拆成楼层后逐条调用 `createChatMessages`。
5. 不用 `setChatMessages` 模拟整段恢复。
6. 不修改备份 JSONL 的 metadata、swipes、时间戳、隐藏状态或扩展字段。
7. 不在导入前切换或关闭当前聊天。
8. 不提供无预览、无确认的一键清空全部备份。
9. 不在本方案中处理事故根因；跳转竞态与聊天清空问题仍属于独立排查事项。

## 四、依赖的 SillyTavern 原生能力

优先复用 SillyTavern 已有备份浏览与聊天导入能力：

| 能力 | 原生接口/函数 | 用途 |
| --- | --- | --- |
| 列出聊天备份 | `POST /api/backups/chat/get` | 取得文件名、大小、楼层数、最后消息时间等摘要 |
| 下载单个备份 | `POST /api/backups/chat/download` | 阅读或导入时按需获取 JSONL |
| 删除单个备份 | `POST /api/backups/chat/delete` | 用户确认后永久删除 `backups` 中指定的聊天备份 |
| 导入角色聊天 | `importCharacterChat(formData, { refresh: false })` | 将原始 JSONL 交给酒馆导入到指定角色卡 |
| 导入群聊 | `importGroupChat(formData, { refresh: false })` | 后续确认支持群聊时复用 |

运行时若缺少备份接口，应显示“当前 SillyTavern 版本不支持备份书架”，不能退回到浏览器任意目录读取，也不能静默显示空书架。可提供“手动选择 JSONL 阅读”的兼容入口，但手动文件不得自动推断导入目标。

## 五、页面结构

### 5.1 首页：角色卡书架

首页只按角色卡显示分组入口，不直接展开备份。每个入口包含：

- 角色卡头像与角色名。
- 该角色卡的备份数量。
- 最近备份时间。
- 进入该角色备份列表的入口。

匹配冲突、已删除或未识别角色仍作为特殊分组显示，不能因无法自动匹配角色卡而隐藏。首页提供刷新、按角色名或组内文件名搜索、按最近备份或角色名排序，以及“快速清理”入口。

### 5.2 角色备份列表

每本“备份书”显示：

- 备份时间。
- JSONL 文件名。
- 文件大小。
- 聊天楼层数。
- 最后一条消息摘要。
- “阅读”入口。
- 独立的“删除”入口。

进入角色卡后才显示该组的全部备份，默认按时间倒序。删除按钮与阅读按钮必须是两个独立交互目标，不能因点击删除而误入阅读。默认不下载全部备份正文，只使用列表接口返回的摘要。

### 5.3 阅读页

点击备份后才下载该文件，并执行只读解析。阅读页优先复用现有 Reader 的楼层展示、正文清理、目录和上下楼层导航能力，但必须禁用：

- 编辑楼层。
- 创建分支。
- 写回酒馆。
- 任何依赖“当前聊天”的修改动作。

阅读页顶部持续显示：角色卡、备份时间、文件大小、楼层数和“这是备份只读视图”。

阅读正文应占满顶栏与底部工具栏之间的剩余高度，不沿用全局阅读正文的 `48vh` 固定高度。底部只提供“删除此备份”和“导入此备份”；返回统一使用手机顶栏左侧返回键，不在内容区重复放置返回按钮。

### 5.4 导入确认

确认信息至少包含：

- 来源备份文件名。
- 识别出的目标角色卡。
- 备份楼层数和时间。
- 明确提示“将作为一份新聊天导入，不覆盖当前聊天”。

目标角色卡无法唯一识别时，必须让用户从现有角色卡中手动选择；未选择前禁止导入。

导入确认页不重复提供“返回阅读”，只保留确认导入操作；用户使用顶栏返回阅读页。

### 5.5 导入结果

导入成功后显示 SillyTavern 返回的新聊天文件名，并提供：

- 打开导入后的聊天。

“打开导入后的聊天”是独立动作，不能作为导入成功后的自动跳转；实施时还需先完成并验证聊天跳转竞态修复。

### 5.6 快速清理

恢复首页提供全局快速清理；角色备份列表可进入仅限当前分组的快速清理。清理规则为：

```text
实际解析聊天楼层数 <= 用户输入的最大楼层数
```

- 输入必须是大于等于 `0` 的整数，默认值为 `0`。
- metadata-only 备份实际楼层数为 `0`，因此属于“0 层及以下”。
- 空文件、损坏文件、metadata 无效、解析失败、列表计数与实际计数不一致均不视为 `0`，并且不得进入删除候选。
- 先刷新摘要并用摘要粗筛，再下载粗筛候选执行完整 JSONL 解析；只有校验成功且实际楼层数满足阈值的文件才能进入最终候选。
- 删除前按角色分组展示文件名、实际楼层数、时间与候选总数；默认选中合格候选，但允许逐项取消。
- 用户再次确认后逐份调用原生删除接口，不并发批量删除；成功项立即从本地书架移除，失败项保留。
- 批量删除没有回滚能力。结果必须分别列出成功数与失败数，结束后重新读取酒馆备份列表。
- 快速清理页同样只使用顶栏返回，不增加内容区返回按钮。

## 六、角色卡分组规则

SillyTavern 当前聊天备份名遵循：

```text
chat_<经过清理的角色卡头像文件主名>_<时间戳>.jsonl
```

分组采用分层判定：

1. 从运行时角色卡列表读取角色名、头像文件名和角色 ID。
2. 使用与 SillyTavern 服务端一致的规范化规则生成备份前缀。
3. 备份文件名前缀与角色卡唯一匹配时，归入该角色卡书架。
4. 多张角色卡产生相同规范化前缀时，标记为“存在冲突”，不得自动选择导入目标。
5. 无法匹配时归入“已删除或未识别的角色卡”。
6. 群聊备份归入独立的“群聊”分组，不伪装为角色卡备份。

备份正文第一行中的 `character_name` 只能作为辅助显示和人工确认信息，不能单独作为目标角色卡身份，因为角色名可能重复或已改变。

## 七、读取与校验

下载后的 JSONL 在进入阅读或导入确认前必须完成：

1. 文件扩展名和响应类型检查。
2. 按行解析 JSON；忽略末尾空行，但不忽略中间损坏行。
3. 第一行必须符合 SillyTavern 聊天头部基本结构。
4. 统计实际消息楼层并与列表摘要对照。
5. 标记仅有 metadata、零楼层、部分损坏或完全无法解析的备份。
6. 保留原始 Blob 用于导入；阅读模型只能是派生数据，不能反向序列化后导入。

任何校验失败都应阻止导入，并显示失败行号或可理解的原因。阅读时也不能把损坏行静默丢弃后宣称文件完整。

## 八、原生导入流程

角色卡备份的确认导入流程：

1. 再次确认目标角色卡仍然存在且身份未变化。
2. 使用已下载的原始 Blob 构造内存 `File`。
3. 构造 `FormData`：
   - `file_type = jsonl`
   - `avatar = 原始备份 File`
   - `avatar_url = 目标角色卡头像文件名`
   - `character_name = 目标角色卡名称`
   - `user_name = 当前用户名称`
4. 调用 SillyTavern 导出的 `importCharacterChat`，且不要求切换当前角色或关闭当前聊天。
5. 只有原生函数返回非空导入文件名时才视为成功。
6. 导入后重新读取备份列表与目标角色聊天列表，确认新聊天可见。

不得直接请求 `/api/chats/save`，也不得自行决定目标 JSONL 文件名。

## 九、插件作用域数据

第一版只恢复酒馆聊天，不自动迁移小剧场、番外、总结等插件作用域数据。

原因：事故聊天对应的插件数据仍绑定旧聊天 scope，而酒馆原生导入会生成新的聊天 ID。自动复制 scope 会影响多个业务域，应在聊天导入稳定后作为单独的第二阶段功能设计。

后续若增加“复制插件内容到导入聊天”，必须满足：

- 用户单独确认。
- 只复制，不删除旧 scope。
- 导入聊天为空 scope 时才允许整包复制。
- 提交前显示涉及的域和条目数量。
- 使用 08 方案完成的事务式备份导入基础设施。

## 十、安全与并发约束

1. 阅读期间不触发任何聊天保存。
2. 导入按钮单次锁定，防止重复点击产生多份聊天。
3. 导入过程中角色卡列表变化时终止并要求重新确认。
4. 网络失败、接口缺失、解析失败和原生导入返回空结果均必须显式报错。
5. 不把备份正文持久化到插件设置或 localStorage。
6. 离开阅读页后释放大型 Blob 和派生楼层数据。
7. 日志不得输出完整聊天正文，只记录备份文件名、阶段和错误类型。
8. 单条删除必须展示精确文件名、角色分组、备份时间与楼层数，并明确说明“永久删除备份，不影响已有聊天”。
9. 删除请求返回成功前不得乐观移除列表项；重复点击同一文件必须由删除锁阻止。
10. 快速清理先下载并解析候选，再按实际楼层数确认；未知或异常计数永远不得自动折算为 `0`。
11. 批量删除按文件顺序串行执行并记录部分成功结果，不能使用并发请求造成结果不可追踪。

## 十一、实施阶段

### R0：能力封装与只读模型

- 封装备份列表与单文件下载接口。
- 建立备份摘要、角色分组、JSONL 校验类型。
- 为未知角色、重复前缀和损坏备份建立测试。

### R1：备份书架与阅读

- 注册“恢复”App。
- 实现“角色卡分组首页 → 组内备份列表”的两级书架。
- 复用 Reader 组件实现备份只读阅读。
- 完成加载、空状态、错误和版本不支持页面。

### R2：原生导入

- 接入 `importCharacterChat`。
- 增加导入确认、幂等锁和结果页。
- 验证导入不会覆盖当前聊天，也不会删除备份。

### R3：兼容与扩展

- 评估群聊导入。
- 增加手动选择 JSONL 的兼容入口。
- 在独立评审后决定是否增加插件 scope 复制。

### R4：备份删除与快速清理

- 接入酒馆原生 `/api/backups/chat/delete`，提供组内单条删除和阅读页删除。
- 实现全局或当前角色分组范围的阈值清理，阈值采用包含关系 `实际楼层数 <= 输入值`。
- 执行下载解析预检、候选选择、不可逆确认、串行删除、部分失败结果与最终刷新。
- 清除内容区重复后退按钮，并让恢复阅读正文占满可用高度。

### R5：完全一致查重删除

- App 显示名称由“恢复”调整为“酒馆备份管理”，保留 `recovery` 内部 ID、Store ID 与文件目录。
- 全局或当前角色分组可扫描重复备份；只把“同一角色分组、实际楼层数一致、原始 Blob 字节长度一致且 SHA-256 一致”的文件视为重复。
- 不把楼层数相同、最后一句相同、前缀包含、正文相同但 metadata 不同或跨角色文件视为可自动删除的重复项。
- 每个重复组默认保留文件名时间最新的一份，只把其余旧副本列为候选；用户可取消任意候选。
- 删除前重新下载并复核保留文件和候选文件，任一文件消失、损坏、计数变化、长度变化或哈希变化时跳过该组或该候选。
- 查重扫描允许有限并发下载和哈希；实际删除继续串行执行，并与单条删除、阈值清理共享互斥状态。

## 十二、测试与验收

至少覆盖：

1. 全部备份能够按角色卡正确分组。
2. 同名角色、头像改名、角色删除和规范化前缀冲突不会错误归组。
3. metadata-only 备份被识别为零楼层，不能伪装为正常恢复点。
4. 损坏 JSONL 在导入前被拦截并指出问题。
5. 阅读不修改原始 Blob、当前聊天或插件 scope。
6. 导入使用原始备份 Blob，不使用阅读后的派生数据。
7. 导入目标来自明确匹配或用户手动选择的角色卡。
8. 导入成功产生新聊天，原聊天和备份均保持不变；只有独立删除操作能删除原备份。
9. 连续点击只产生一次导入请求。
10. 原生接口不可用时显示版本错误，不静默回退。
11. 360×700、390×844、430×900 三种尺寸完成书架、阅读、确认和结果页视觉验证。
12. UI 改动后运行 `scripts/check-ui-reuse.ps1`，并完成 typecheck、单测、契约检查和 build。
13. 输入阈值 `N` 时只选择实际解析楼层数 `<= N` 的备份；阈值 `0` 只选择真正的 metadata-only。
14. 空文件、损坏文件和列表/实际计数不一致文件不会进入快速清理候选。
15. 单条和批量删除只调用备份删除接口，不调用聊天删除、聊天保存或楼层写入接口。
16. 批量删除部分失败时，成功项、失败项、书架数量和最终刷新结果一致。
17. 角色卡首页、组内备份列表、快速清理、阅读、确认和结果页均完成三种尺寸视觉验证；阅读区无 `48vh` 截短和底部工具栏遮挡。
18. 完全相同的文件只在同一角色分组内归为一组，跨角色、不同 metadata、不同隐藏状态或不同原始字节均不会成为自动删除候选。
19. 重复组保留文件名时间最新的一份；删除前保留项或候选项发生变化时必须跳过，不能继续使用过期扫描结果。
20. 查重结果页展示保留文件、候选文件、预计释放空间以及失败/跳过结果，并完成三种尺寸视觉验证。

## 十三、最终验收标准

用户可以在“酒馆备份管理”App 首页按角色卡进入备份列表，完整阅读后将原始备份通过 SillyTavern 原生接口导入为目标角色卡下的一份新聊天；也可以在明确确认后单独删除备份、按实际楼层阈值安全清理小备份，或只删除通过完整字节哈希确认的旧重复副本。导入过程不覆盖、不删除、不直接写聊天文件；删除过程只作用于用户明确选择的酒馆备份，不改变已有聊天或旧插件 scope 数据。

## 十四、完成记录与交接

### 14.1 已完成实现

1. 新增独立的备份管理 App，并注册到内置 App 与教程目录；R5 将显示名称更新为“酒馆备份管理”，内部 ID 仍为 `recovery`。
2. 首页通过酒馆备份列表接口读取全部 `chat_*.jsonl` 摘要，只显示角色卡或特殊分组、备份数量与最近时间；进入分组后再显示备份列表。重复前缀显示为冲突，无法匹配的备份保留在“已删除或未识别的角色卡”。
3. 点击备份后才下载原始 Blob，严格逐行解析 JSONL，并复用只读阅读壳、楼层目录和上下层导航。
4. metadata-only、空文件、无效 metadata 头、中间空行或损坏 JSON 行、列表楼层数与实际楼层数不一致都会阻止导入并显示原因。
5. 导入前要求明确目标角色卡，并在提交前重新加载角色列表，核验角色 ID、头像文件名和名称没有变化。
6. 导入只把下载到的原始 Blob 包装为内存 `File`，交给 `importCharacterChat(formData, { refresh: false })`；没有使用阅读派生数据重新序列化。
7. 导入过程不会调用聊天保存、聊天删除、备份删除、关闭当前聊天或楼层写入接口，也不会持久化备份正文；备份删除是与导入隔离的用户显式操作。
8. 导入使用 single-flight 锁。酒馆已返回新聊天文件名后，即使后续可见性确认失败，也会记录本次成功并禁止同一会话重复导入；结果页会提示用户检查，不会误导其再次点击。
9. 导入后只在用户单独点击且酒馆已确认新聊天可见时，才使用 08 中完成的安全跳转函数打开新聊天。
10. 组内列表与阅读页均可在明确确认后调用酒馆原生 `/api/backups/chat/delete` 永久删除单份备份；成功响应前不从书架移除，删除不会触碰已有聊天。
11. 首页和组内列表均可进入快速清理。阈值采用 `实际楼层数 <= 输入值`；摘要粗筛后会逐份下载解析，metadata-only 计为 0，空文件、损坏文件和计数不一致文件全部排除。
12. 快速清理默认选中安全候选并允许取消，确认后再次下载校验、串行删除并分别记录成功和失败，最后刷新酒馆备份列表。
13. 首页改为“角色卡 → 备份”两级目录；阅读、确认、结果和空状态移除内容区重复返回按钮。恢复阅读页单独解除全局 `48vh` 正文高度，填满剩余可用空间。
14. App 显示名称更新为“酒馆备份管理”，首页新增“清理小备份”和“查找重复备份”两个明确入口，角色分组页也可限定当前角色执行查重。
15. 查重扫描对粗筛候选有限并发下载，严格解析原始 JSONL，并用原始 Blob 字节长度与 SHA-256 分组；每组按文件名备份时间保留最新一份，其余旧副本默认选中且允许取消。
16. 查重删除与单条删除、阈值清理共享互斥状态。确认后先复核保留文件，再逐份复核候选文件；哈希、长度、实际楼层数或角色分组变化时跳过，不调用聊天删除或聊天保存接口。

### 14.2 R3 评估结论

- **群聊专用导入**：暂不启用。当前备份列表摘要和文件名不足以可靠证明某份备份的群聊身份，不能在高风险恢复流程中自动猜测并调用群聊导入。
- **手动选择任意 JSONL**：首版不启用。当前需求是读取酒馆 `backups` 中的聊天备份；接口不可用时明确显示版本错误，不扩大到浏览器任意文件导入。
- **插件 scope 复制**：明确不启用。小剧场、番外等旧 scope 继续保留，若以后迁移必须另立方案并再次确认。

这些项目不影响首版“备份书架 → 只读确认 → 原生导入为角色卡新聊天”的完整闭环。

### 14.5 R6 双入口、设置快照与续长查重

1. “酒馆备份管理”首页改为两个独立入口：“聊天备份”和“设置快照”。聊天备份进入后仍按角色分组；设置快照独立列出 `settings_*.json`，避免将聊天导入与设置恢复混为一类。
2. 设置快照使用酒馆原生 `/api/settings/get-snapshots`、`load-snapshot`、`make-snapshot` 和 `restore-snapshot` 接口，可阅读格式化 JSON、手动新建快照和明确确认后恢复。
3. 恢复只覆盖酒馆设置文件，完成后明确提示刷新整个酒馆页面。若用户需要保留当前设置，界面要求先返回列表手动“新建”；不在恢复动作中自动新建，因为酒馆达到保留上限时会清理最旧快照，可能误删正要恢复的目标。
4. 设置快照查重逐份读取原始文本并计算 SHA-256，只删除完全一致的旧副本，每组固定保留时间最新的一份。删除前重新读取保留项与候选项复核。
5. 设置快照删除不猜测文件路径，使用酒馆原生 `/api/data-maid/report` 返回的一次性令牌和文件哈希，再调用 `/api/data-maid/delete`；删除后重新拉取列表确认结果，并最终释放令牌。
6. 聊天查重增加“续长包含候选”：仅当同一角色内较短备份的每条原始 JSONL 消息行都严格等于较长备份开头，且较长备份确实新增楼层时成立。metadata-only、分支改写、重排或任一行变化均不成立。
7. 续长候选默认不勾选。用户可分别进入较短版和保留版阅读；删除前重新下载双方，再次验证严格前缀关系。
8. 完全查重、续长查重和按楼层清理的候选行均可直接进入现有只读聊天阅读页；阅读页通过路由栈返回原扫描结果，保留勾选状态和页面上下文。
