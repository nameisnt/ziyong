> 历史归档：本方案已完成，仅用于追溯 2026-08-11 至 2026-08-12 的实施过程，不得作为当前待办或自动执行依据。当前要求以 `docs/07-当前代码与UI复用审计及设计要求.md` 为准。

更新日期：2026-08-11

完成状态：**已完成（P0—P6 均已按本文验收口径收口）**

本文用于新会话继续整改当前项目，汇总代码结构审计、UI 复用审计和导入导出安全分析。执行时必须同时遵守根目录
`AGENTS.md`、`.agents/AGENT-v2.md` 与 `docs/07-当前代码与UI复用审计及设计要求.md`。

本文不是要求一次性重写全部代码。目标是先守住数据完整性，再逐步消除并行流程、静默失败和半完成的组件拆分。

## 一、开始前的状态检查

新会话开始后先完成以下检查，不要立即编辑：

1. 运行 `git status --short --branch`，确认当前分支和已有未提交修改。
2. 不撤销、不覆盖用户已有改动；需要修改同一文件时先阅读当前版本。
3. 阅读本文件列出的核心文件及相关 Schema，不以旧截图或旧方案文档推测当前实现。
4. 修改数据结构前先保留当前可恢复副本，并确认备份文件不是“当前聊天备份冒充完整备份”。
5. 一次只完成一个结构阶段；每阶段完成后执行针对性验证、lint、build 和最小浏览器冒烟。

## 二、必须保持的系统不变量

后续修改应围绕以下不变量展开：

1. 同一生成请求只能经过一个共享执行生命周期。
2. 配置解析失败必须显式暴露，不能静默替换成空白默认值。
3. 聊天数据和全局配置必须由类型和注册信息明确区分，不能靠数据形状猜测。
4. 导入必须先完整校验，再统一提交；任一域失败时不能留下半恢复状态。
5. 当前聊天备份不能执行完整恢复。
6. “清空生成内容”只能清除内容和草稿，不能触碰配置、规则、主题或工作台。
7. 主题状态只能有一个行为实现，App 页面不得各自重新解释同一设置。
8. 动态列表统一使用可搜索选择器；原生 `select` 只保留给短小固定枚举。
9. 根组件负责路由协调，不同时承担生成事务、持久化、编辑草稿和版本业务。
10. 兼容回退必须有明确边界、保留原始错误，并在所有回退失败后抛出可定位错误。

## 三、当前已确认的代码结构问题

### 3.1 两套生成执行流程已经产生行为差异

核心文件：

- `src/core/generationService.ts`
- `src/apps/card-writer/CardWriterApp.vue`

`generateContent()`
负责当前聊天检查、恢复事务、限流、429 重试、取消、解析、失败草稿和保存；`generateOrderedPromptContent()`
另行实现限流、取消、流式监听和请求发送，但缺少部分共同保障。

根因不是写卡提示词特殊，而是“提示词构造策略”和“请求生命周期”没有分开。

目标结构：

- `executeGeneration()`：唯一的限流、重试、取消、生命周期和错误处理入口。
- 普通 App 策略：从捕获结果构造 ordered prompts。
- 写卡策略：接收已经排好顺序的 prompts。
- 是否允许历史聊天、是否需要可见性事务等差异必须作为显式策略参数，不能通过绕开主流程实现。

### 3.2 配置读取存在静默默认值

重点文件：

- `src/apps/chat-insert/store.ts`
- `src/apps/workbench/store.ts`
- `src/apps/timekeeper/store.ts`
- `src/apps/comfy/store.ts`

这些 Store 在解析异常时可能直接返回默认配置。版本迁移失败、用户数据损坏和程序错误因此都表现为“没有数据”。后续保存还可能覆盖原始内容。

目标结构：

- Schema 解析与版本迁移返回明确结果。
- 失败时保留原始数据，不自动持久化空默认值。
- 页面显示可读错误，并提供导出原始数据、重试迁移或确认重置入口。
- 只有首次安装且字段确实不存在时才能创建默认值。

不能把所有裸 `catch {}`
机械删除。跨 frame 能力探测、旧世界书原始 API 回退等有明确边界的捕获可以保留，但必须说明原因并保留最终错误。

### 3.3 根组件仍承担过多职责

优先文件：

- `src/components/ExtrasApp.vue`
- `src/components/ForumApp.vue`
- `src/components/PromptsApp.vue`
- 其次检查 `DiaryApp.vue`、`TheaterApp.vue`、`LettersApp.vue`、`SummaryApp.vue`

当前已经拆出部分页面和 composable，但根组件仍同时持有路由、编辑草稿、生成、预览、重写、版本、删除、引用和失败草稿逻辑。

拆分标准不是文件行数，而是业务责任：

- 路由协调组件只解析 route、定位实体并组合页面。
- 页面组件只负责该页面的交互和局部状态。
- composable 只封装可复用的页面会话状态。
- 生成、版本删除、导入等业务事务放入可独立测试的用例函数或服务。
- 拆分后删除旧分支，不能保留第二套兼容实现。

### 3.4 主题隔离依赖高权重 CSS

重点文件：

- `src/global.css`
- `src/components/PhoneOverlay.vue`
- `src/apps/theme/ThemeApp.vue`
- `src/components/settings/SettingsGeneralPanel.vue`
- `src/store/settings.ts`

当前全局 `!important` 已达到守卫上限 22/22，高特异性重复根选择器为 32/33。守卫现在只是冻结债务，并未消除债务。

目标结构：

- `settingsStore` 负责字体、壁纸和主题选择值的唯一解析与切换。
- 主题 App 管理资源和完整方案；设置页只提供高频入口。
- `PhoneOverlay` 只把权威状态映射成 CSS 变量和必要资源。
- 逐批降低高特异性规则，同时把守卫阈值向下收紧。
- 禁止再用增加 `.pc-phone-root` 次数或新增 `!important` 解决主题问题。

### 3.5 动态选择控件仍未统一

重点文件：

- `src/apps/workbench/WorkbenchApp.vue`
- `src/apps/comfy/ComfyApp.vue`
- `src/components/settings/SettingsConnectionPanel.vue`

目前仍有大量原生 `select` 用于 API 配置、预设、书架、世界书、模型和工作流等动态数据。

目标结构：

- 固定枚举继续使用 `.pc-select`。
- 动态数据统一使用 `SearchableCombobox` 或共享搜索选择覆盖层。
- 建立统一 option 结构，保留失效值的显示和修复能力。
- 不在每个 App 内重复编写搜索、展开、键盘和滚动恢复逻辑。

### 3.6 测试覆盖偏向几何截图

重点文件：

- `src/testing/visual-harness.ts`
- `scripts/ui-visual-check.mjs`
- `package.json`

视觉场景覆盖较多，但测试协调器本身超过四千行，并且自动检查主要关注溢出、尺寸和可触达性。当前缺少正式的单元测试和独立 typecheck 命令。

优先补充以下行为测试：

- 生成执行生命周期和 429 重试。
- 配置迁移失败不覆盖原始数据。
- 聊天改名与 scope 迁移。
- 版本删除与生成记录同步。
- 完整备份、当前聊天备份和错误备份的导入行为。
- 任一备份域失败时整体回滚。

## 四、导入导出的核心结构问题

### 4.1 `PhoneBackupDomain` 混合了不同性质的数据

当前 `PhoneBackupDomain` 只有 `key`、`exportData`、`importData`
和可选 rehydrate。全局配置、聊天内容、临时草稿、主题和工作台因此被当作同一种数据处理。

需要扩展为类似以下契约：

```ts
type PhoneBackupDomain = {
  key: string;
  scope: 'global' | 'chat';
  category: 'configuration' | 'content' | 'draft';
  schemaVersion: number;
  schema: z.ZodType<unknown>;
  exportData(context: BackupExportContext): unknown;
  stageImport(data: unknown, context: BackupImportContext): StagedDomainImport;
  rehydrateFromSettings?: () => void;
};
```

具体命名可以调整，但 `scope`、`category`、版本和校验能力不能缺失。

### 4.2 当前聊天备份与完整备份无法区分

重点文件：

- `src/util/backup.ts`
- `src/type/backup.ts`
- `src/components/settings/SettingsGeneralPanel.vue`

两种备份都使用相同
`schemaVersion: 1`。当前聊天备份只保留一个 scope，但仍能进入完整恢复流程。全局域在当前聊天备份中还会被错误转换为空聊天信封。

必须增加：

```ts
backupKind: 'full' | 'current-chat';
```

导入规则：

- `current-chat` 只能导入到当前聊天。
- `full` 可以完整恢复，也可以选择其中一个聊天导入。
- UI 必须根据文件类型展示对应操作，不能只依赖用户记住自己导出的是什么。
- 对现有没有 `backupKind` 的 v1 文件，需要保守识别并让用户确认，不能默认当完整备份。

### 4.3 导入没有事务和回滚

当前 `applyPhoneBackup()` 和 `importPhoneBackupScopeToCurrentChat()` 逐项直接写入
`extension_settings`。中途失败会留下半恢复状态。

推荐流程：

1. 解析 JSON 与总 Schema。
2. 检查备份类型和版本。
3. 对所有目标域执行 Schema 校验与迁移，只生成 staged data，不写入设置。
4. 生成导入计划，列出覆盖范围、跳过域和缺失资源。
5. 在内存中克隆所有将被修改的旧数据。
6. 一次性提交 staged data。
7. 统一 rehydrate。
8. 任一步失败则恢复旧快照并抛出原始错误。
9. 保存成功后再显示“恢复完成”。

禁止在校验阶段调用会修改 Store 或 `extension_settings` 的函数。

### 4.4 扩展域缺少统一校验

`PhoneBackupSchema.data.domains` 当前允许任意 unknown。许多 `importData` 只是直接 `_.set`，错误通常推迟到 Store
rehydrate 时才暴露，部分 Store又会静默回默认值。

每个域必须自行声明 Schema 和迁移函数。总备份 Schema 只验证 manifest；具体域由注册表统一预检。这样新增 App 不需要修改中心大 Schema，但也不能绕过校验。

### 4.5 “清空全部生成内容”会遍历所有备份域

`clearAllPhoneGeneratedContent()` 当前通过全部 backup domain 执行空信封导入。由于 backup
domain 同时包含配置，可能重置工作台、条目库、正则、预设绑定、写卡工坊等内容。

修复后只能选择：

```ts
domain.category === 'content' || domain.category === 'draft';
```

全局配置不参与清空生成内容。清空前的确认文案应由实际将删除的域生成。

### 4.6 备份不包含密钥和二进制资源

当前有意排除：

- 外部 API Key。
- 云媒体 API Key。
- 自定义字体文件。
- 自定义壁纸文件。
- 已生成媒体文件。

密钥排除必须保持。完整备份中可以保留连接配置名称、URL、模型等非秘密信息，但导入后应明确提示重新填写密钥。

字体、壁纸和媒体不能伪装成已经完整备份。建议在 manifest 中记录缺失资源摘要，并把按钮文案改为“导出手机配置与内容”，或在导出前明确显示不包含的项目。

## 五、推荐实施顺序

### P0：先消除备份误操作和清空风险

涉及文件：

- `src/core/appRegistry.ts`
- `src/type/backup.ts`
- `src/util/backup.ts`
- 所有注册 `backupDomains` 的 `index.ts`
- `SettingsGeneralPanel.vue`
- `SettingsAdvancedPanel.vue`

完成标准：

- 当前聊天备份不能完整恢复。
- 当前聊天导出只处理 chat scope 域。
- 清空生成内容不会修改任何 configuration 域。
- 域 key 重复时注册阶段直接报错。
- 旧 v1 备份有明确兼容策略。

### P1：建立事务式导入

完成 Schema 注册、全量预检、导入计划、内存快照、统一提交和失败回滚。先覆盖完整恢复，再复用到当前聊天导入。

### P2：统一生成执行生命周期

合并 `generateContent()` 与 `generateOrderedPromptContent()` 的公共执行部分，并为普通生成和写卡分别保留提示词构造策略。

### P3：移除静默配置回退

先处理工作台、时间确认、ComfyUI 和聊天插入。为真实旧数据建立显式迁移，不接受“解析失败就当首次安装”。

### P4：继续完成根组件拆分

按番外、论坛、提示词工坊的高风险业务用例逐个拆分。每次只迁移一个完整用例，并删除旧实现。

### P5：收敛主题和动态控件

统一主题行为入口，逐步降低 CSS 权重；把动态原生 select 替换为共享搜索选择器。

### P6：拆分测试基础设施

建立单元测试、独立 typecheck，并把视觉场景按 App 拆分 fixture 与断言。测试迁移必须伴随前述每个阶段进行，不能等全部重构完成后再补。

## 六、导入导出验收矩阵

至少覆盖以下场景：

| 场景                     | 预期结果                                       |
| ------------------------ | ---------------------------------------------- |
| 完整备份执行完整恢复     | 设置与所有合法域恢复成功                       |
| 当前聊天备份点击完整恢复 | UI 不提供该操作，底层也必须拒绝                |
| 完整备份选择单个聊天导入 | 只覆盖当前聊天的对应 chat 域                   |
| 某个域 Schema 错误       | 写入前失败，现有数据完全不变                   |
| 提交中途模拟异常         | 自动回滚，现有数据完全恢复                     |
| 备份缺少某个新增 App 域  | 保留当前该域数据，并明确显示跳过               |
| 备份包含未知域           | 保留兼容信息或明确跳过，不执行未知数据         |
| 旧 v1 备份               | 经迁移后导入，或给出可理解的不支持原因         |
| API 配置含密钥           | 导出文件中密钥为空，导入后提示重新填写         |
| 自定义字体和壁纸         | 不伪装为已恢复，显示缺失资源提示               |
| 清空当前聊天             | 不影响其他聊天和全局配置                       |
| 清空全部生成内容         | 不影响工作台、条目库、正则、主题、连接和提示词 |

## 七、禁止采用的补丁方式

1. 只在 UI 增加一句警告，但底层仍允许错误备份类型导入。
2. 根据对象里有没有 `scopes` 临时猜测它是全局域还是聊天域。
3. 给 `applyPhoneBackup()` 再包一层大 `try/catch`，出错后只显示 toast。
4. 导入失败后用默认值“保证界面能打开”。
5. 为每个 App 各写一套备份按钮和 JSON 解析流程。
6. 继续把新域直接声明成 `z.unknown()` 后写入设置。
7. 为修主题继续增加 `!important` 或重复根选择器。
8. 为拆文件而拆文件，但让两个文件共同维护同一份业务状态。

## 八、每阶段验证要求

每次修改后按适用范围执行：

1. 新增的针对性单元测试。
2. typecheck；当前缺少脚本时应先建立明确的类型检查命令。
3. `pnpm lint`。
4. `powershell -ExecutionPolicy Bypass -File scripts/check-ui-reuse.ps1`。
5. `pnpm style:check`。
6. `pnpm build`。
7. 用浏览器真实执行一次对应导出、导入或 App 工作流，不以服务启动成功代替验证。
8. 检查 git diff，确认没有第二套流程、静默回退、无关重排或意外生成文件。

## 九、交给新会话的建议起点

新会话第一项实现应选择 **P0：备份域分类与备份类型保护**。先不要同时拆生成服务或大型 Vue 组件。

建议第一轮只完成：

1. 为 `PhoneBackupDomain` 增加 `scope` 与 `category`。
2. 为备份增加 `backupKind`。
3. 修正当前聊天导出，只导出 chat scope 域。
4. 阻止当前聊天备份进入完整恢复。
5. 修正清空逻辑，只清除 content/draft 域。
6. 为上述行为建立自动测试。

第一轮稳定后，再进入事务式导入。这样可以先封住最直接的数据丢失入口，同时避免一次改动跨越生成、UI 和全部业务 Store。

## 十一、聊天楼层丢失事故记录与结论

用户报告某聊天内的酒馆楼层全部丢失，但小剧场和番外等插件内数据仍保留。已知线索：

1. 曾从插件直接跳转。
2. 曾将“来源楼层模式”设为“不使用聊天楼层”，具体时点未知。
3. 此前在另一个角色卡删除一个聊天并新建聊天；随后仅打开世界书联动并修改条目内容。

只读排查与用户现场确认结果：事故聊天对应 JSONL 最终只剩 metadata，但在酒馆 `default-user/backups`
中找到了事故前聊天备份，说明丢失的是酒馆聊天文件内容，插件自身的小剧场、番外等聊天 scope 数据并未同步丢失。

结论：

1. “不使用聊天楼层”只控制生成时的来源读取，不包含删除或清空酒馆楼层的写入，因此不是直接原因。
2. 世界书联动修改条目没有发现清空当前聊天 JSONL 的调用证据；另一个角色卡中的删除聊天操作也不足以单独解释本聊天被清空。
3. 旧版插件直接跳转存在明确高风险竞态：可能先关闭当前聊天，再通过隐藏 DOM 和固定延迟触发目标聊天，且整个过程既不等待也不核验结果。现有证据无法证明它就是本次事故的唯一原因，但该路径与事故操作序列相交，已作为必须消除的风险完成整改。
4. 由于酒馆没有为这几分钟内的每次聊天文件写入保留可归因审计日志，不能从现存文件反推出唯一写入者；因此事故根因保留为“直接跳转竞态高度可疑但无法定案”，不把猜测写成确定事实。
5. 后续恢复能力不在本方案内直接覆盖原聊天；方案 10 将以只读备份书架、内容阅读确认和酒馆原生导入为边界，不直接写、删、替换 chats 目录文件。
