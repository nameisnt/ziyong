# 当前代码与 UI 复用审计及设计要求

审计日期：2026-08-11

本文档是当前项目关于代码复用、UI 复用、UI 设计要求和结构问题的唯一总则。组件参数与 App 注册字段的详细说明仍查阅：

- `02-App注册与能力复用.md`
- `06-Web UI复用组件.md`

执行时必须同时遵守根目录 `AGENTS.md` 和本文。若旧代码、截图或其他说明与本文冲突，以执行指令和本文为准。

## 一、审计原则

本次审计按以下原则判断，不以“当前能运行”作为质量合格标准：

1. 单一事实来源：同一状态、校验、路由、主题和生成流程只能有一个权威实现。
2. 优先减法：先删除重复结构、过时分支和无意义说明，再考虑增加组件或配置。
3. 根因修复：跨 App 重复、状态同步、数据迁移和共享流程属于结构问题，不能继续用局部覆盖补丁处理。
4. 显式失败：运行时边界允许兼容探测，但业务失败不能被空 `catch`、静默默认值或伪成功吞掉。
5. 小而完整：修改范围应聚焦，但必须完成实现、验证和遗留清理，不能留下第二套并行逻辑。
6. 可验证：优先使用行为断言、类型检查、构建和可复现的视觉场景，不以人工观感代替验证。

## 三、当前代码复用情况

### 3.1 已经形成的可靠复用

#### App 能力注册

`src/core/appRegistry.ts` 和 `src/data/apps.ts` 已经把 App 从中心硬编码列表中拆出。当前注册能力覆盖：

- `backupDomains`：28 处
- `generationProvider`：14 处
- `referenceProvider`：16 处
- `contentReceiver`：13 处
- `contentStatsProvider`：14 处
- `favoriteProvider`：10 处
- `scopeSwitchHandler`：17 处
- `resetCurrentScope`：20 处

这是当前最成熟的结构。新增跨 App 能力应继续挂在注册模块上，由聚合页面消费，禁止让来源 App 直接导入目标 App 的 store。

#### 数据作用域

`useChatScopedDomain`
已被总结、日记、番外、论坛、小剧场、书信、资料表、世界书槽位等聊天相关域复用。它统一处理聊天切换、兼容作用域和持久化，是聊天数据的权威边界。

全局数据与聊天数据必须继续明确区分。任何“切换聊天后数据消失、串到上一聊天或改名后留下旧档案”的问题，都应先检查 scope 身份与迁移，不应在页面层复制一份状态兜底。

#### 生成管线

`generationService.ts`、生成 adapter、任务模板、类型提示词、连接覆盖和引用格式化已经构成共享生成管线。

当前复用情况：

- `GenerationPanel`：10 个页面文件使用
- `GenerationPreviewPanel`：10 个页面文件使用
- `useGenerationReplaySession`：论坛、番外、小剧场、书信使用
- `FailedDraftList`：14 个页面文件使用
- `ReferencePicker`：由生成面板间接复用，并有 5 个页面直接使用

生成 App 不应自行重新实现来源楼层、连接覆盖、预设覆盖、引用、失败草稿和离开预览确认。

#### 阅读与详情

`ReaderDetailShell` 已被 8 个详情页面使用，统一了承载正文、版本导航和底部操作区。`useDetailScroll`
被 8 个业务页面使用，目录与详情位置恢复也已有共享 composable。

详情页后续应继续向“协调器 + 页面组件 + composable”收敛，不应把目录、编辑、重写、版本和删除都重新塞回根 App。

#### 基础 UI

全局控件类已经得到广泛使用：

- `.pc-primary-btn`：约 105 次
- `.pc-soft-btn`：约 233 次
- `.pc-icon-btn`：约 234 次
- `.pc-field`：约 528 次
- `.pc-form-actions`：约 89 次
- `.pc-list-row`：约 51 次
- `.pc-toggle`：约 46 次

组件复用也已具备规模：

- `EmptyState`：52 个页面文件
- `SearchableCombobox`：29 个页面文件
- `InfoHint`：23 个页面文件
- `CatalogModal`：6 个页面文件

卡片滥用已经明显减少。当前 `.pc-section-card`
约 27 次，主要用于预览、状态和独立对象；没有发现普遍的卡片套卡片结构。后续不应反弹。

### 3.2 仍属于“外观复用，流程未复用”的区域

多个 App 虽然使用相同按钮和生成面板，但根组件仍各自维护：

- 路由分支与页面切换
- 生成状态初始化和清理
- 失败草稿重新解析
- 预览保存和返回调整
- 删除确认与提示
- 版本重写恢复

相同函数名在多个页面重复出现，例如
`stopGeneration`、`runGeneration`、`savePreview`、`reparseFailedDraft`。函数同名本身不是问题，但它说明共享组件目前更多统一了外观，没有完全统一生命周期不变量。

抽取前必须先确认共享不变量。不要为了减少行数制造一个带十几个参数的万能 composable。

## 四、当前主要代码问题

### P1：根 App 和核心协调器过重

以下文件已经同时承担模板、路由、业务状态、持久化协调和大量样式：

| 文件                                    | 行数 |
| --------------------------------------- | ---: |
| `components/ExtrasApp.vue`              | 2114 |
| `components/PromptsApp.vue`             | 2055 |
| `apps/theme/ThemeApp.vue`               | 1840 |
| `components/ForumApp.vue`               | 1699 |
| `components/PhoneOverlay.vue`           | 1650 |
| `components/ReaderApp.vue`              | 1494 |
| `components/DiaryApp.vue`               | 1420 |
| `components/TheaterApp.vue`             | 1373 |
| `apps/relationship/RelationshipApp.vue` | 1280 |
| `apps/app-builder/CustomAppHost.vue`    | 1244 |
| `apps/workbench/WorkbenchApp.vue`       | 1230 |

问题不是单纯“文件太长”，而是修改一个页面状态时容易影响其他 route、滚动恢复、草稿和预览会话。结构修复的目标应是：

- 根组件只解析 route、选择页面和协调跨页状态。
- 页面组件只负责当前页面的输入与事件。
- 业务转换、生成配置和持久化进入可测试函数或 composable。
- CSS 跟随实际页面组件，不继续堆在根组件末尾。

### P1：错误处理存在静默失败

`src` 中有 63 处裸
`catch {}`。其中一部分属于运行时能力探测、剪贴板降级或 JSON 候选解析，可以合理保留；另一部分位于 store、API 和业务操作中，可能让“点击没反应”再次出现。

符合本文的处理要求：

- 能力探测失败：返回明确的“不支持”结果，可选择记录 debug 信息。
- 用户触发操作失败：必须进入页面错误状态或通知系统。
- 数据解析失败：保留原始输入和可重新解析草稿。
- 队列尾部吞错只允许用于防止 Promise 链永久断裂，原任务仍必须把错误交给调用方。
- 禁止用默认成功对象掩盖失败。

### P1：主题隔离依赖高特异性补丁

`src/global.css` 当前有 22 个 `!important`，并使用 32 处四次以上重复 `.pc-phone-root`
的高特异性选择器。它解决了酒馆主题污染手机表单和字体的问题，但已经非常接近守卫上限。

这说明主题边界仍然脆弱：

- 酒馆主题规则可以进入手机内部。
- 手机只能继续提高选择器权重反压。
- 字体、输入框和阅读器样式容易在不同主题下出现回归。

在未验证浏览器兼容和打包方式前，不进行大规模 Shadow DOM 改造；但任何新样式都不得增加重复根选择器或
`!important`。新增主题能力必须从 `PhoneOverlay` 的变量边界进入。

### P1：动态下拉仍有两套实现

当前还有 65 个原生 `<select>`。固定且选项很少的枚举使用 `.pc-select` 没有问题，但以下动态资源不符合现有交互要求：

- 工作台：24 个 select，包含预设、API 配置、资料表、书架、论坛板块、类型和工作流。
- ComfyUI：8 个 select，包含工作流、模型、采样器和调度器。
- 云媒体：7 个 select，包含配置与服务资源。
- 设置：外部 API 配置、酒馆预设、字体和壁纸资源。
- 资料表、主题和媒体生成中的动态列表。

动态资源必须使用 `SearchableCombobox`；只有 2 到 4 个固定模式使用分段控件，固定短枚举才使用
`.pc-select`。替换时应先统一选项模型，不要在每个页面重复适配。

### P1：视觉测试偏重截图，缺少语义门槛

现有 181 个 390x844 场景都通过 DOM 几何检查，说明手机壳越界、横向滚动和不可触达控件控制得较好。但当前检查无法判断：

- 卡片是否使用合理
- 说明文字是否多余
- 操作是否拥挤或重复
- 动态下拉是否可搜索
- 对比度是否足够
- 标题与信息层级是否正确
- 暗色主题下输入框和弹窗是否可读

`visual-harness.ts`
已达到 4191 行并用大型条件分支维护约 153 个场景行为，新增测试容易修改同一个热点文件。场景 fixture、行为断言和截图编排应按业务域拆分，主 harness 只负责注册与运行。

### P2：目录结构仍有新旧两套

新 App 多放在 `src/apps/<id>`，部分核心创作 App 仍以 `src/components/*App.vue` 加 `src/apps/builtin.ts`
注册。两种方式都能运行，但会增加定位成本，也让页面拆分程度不一致。

处理原则：修改某个旧 App 的结构性功能时再迁移，不做一次性目录搬家。迁移完成后删除旧入口，不能保留转发层和第二注册点。

### P2：设置与主题存在重复控制面

壁纸、字体和阅读器字体同时涉及 `ThemeApp`、`SettingsGeneralPanel`、`SettingsInterfacePanel` 和
`PhoneOverlay`。数据目前主要汇总到 settings，但控件与事件处理分散，历史上已经出现“手机字体生效、阅读器字体不生效”和酒馆主题污染输入框的问题。

要求：

- settings store 是唯一状态来源。
- Theme App 负责主题方案与视觉资源管理。
- 设置 App 只保留高频开关和当前值入口，不复制完整编辑器。
- `PhoneOverlay` 只负责把状态转换为 CSS 变量，不拥有另一套配置。

### P2：局部样式维护面仍然过大

159 个 Vue 文件中有 146 个 scoped style，估算约 13245 行。局部布局本身合理，但部分文件的样式规模已经接近独立样式系统：

- `PromptsApp.vue`：约 651 行样式
- `PhoneOverlay.vue`：约 576 行样式
- `ReaderApp.vue`：约 572 行样式
- `ThemeApp.vue`：约 529 行样式
- `ReferencePicker.vue`：约 368 行样式
- `BaguScanPanel.vue`：约 364 行样式

不能只按相同类名判断重复。重复的“左标题右操作”“目录工具栏”“字段行”“固定底部操作区”和“空状态边界”也应优先复用全局布局类或小组件。

## 五、当前 UI 评价

### 已经做对的部分

- 整体已经从卡片堆叠转向无框页面小节和列表行。
- 顶栏承担 App 标题，多数页面不再重复大标题。
- 主按钮、软按钮、图标按钮、输入框和开关的视觉语言基本一致。
- 首页、提示词、主题、资料表和 App 工坊的首屏层级清楚。
- 详情阅读、版本导航和底栏已经形成共享骨架。
- 当前全量场景没有发现手机壳越界或横向滚动。

### 仍需修正的部分

- 首页每个空 App 都显示“暂无内容”，重复信息形成视觉噪音。空状态应在进入 App 后表达，首页副文案只在有有效统计时显示。
- 工作台空页面同时显示“0 个工作流”、大空状态、运行日志“0 条”和另一空状态，重复表达相同事实并制造大面积无意义留白。
- 设置页部分图标命令过密，导入、导出、编辑、删除依赖图标猜测；不可用操作仍占据明显位置。图标必须有 title 和 aria-label，低频操作应进入动作菜单。
- 写卡工坊等长表单虽然已经扁平化，但仍需要更稳定的分组折叠和固定提交区，避免用户滚到页面底部才能确认生成状态。
- 提示词 App 的 App 网格适合做入口，但进入管理页后应切换为高密度列表，不应继续使用同尺寸入口卡。
- 主题 App 的预览卡和色板属于真实对象，可以保留卡片；普通设置行不能照搬这种表现。
- 动态资源列表仍使用原生 select，选项一多就难以搜索，也会受酒馆主题影响。

## 六、UI 设计硬要求

### 6.1 页面层级

- App 顶部标题由手机顶栏提供，页面内不重复同名 H1 或大横幅。
- 页面第一屏直接提供主要任务，不放欢迎页和功能说明卡。
- 页面使用 `12px` 到 `14px` 的稳定间距，不用大块空白制造层级。
- 业务上下文只保留一行；详细说明进入 `InfoHint`、折叠高级设置或教程。

### 6.2 卡片使用

只在以下对象使用卡片边界：

- 可重复的独立内容对象
- 预览结果
- 错误、警告或任务状态
- 模态弹窗
- 主题、媒体和真实可视化对象

页面分组、普通字段组、工具栏和统计行默认无卡片。禁止卡片套卡片，也禁止为了填满空白制造说明卡。

### 6.3 控件选择

- 提交、生成、保存：`.pc-primary-btn`
- 取消和普通命令：`.pc-soft-btn`
- 刷新、编辑、删除、复制、排序：`.pc-icon-btn`
- 二元状态：`.pc-toggle`
- 2 到 4 个高频互斥模式：`.pc-segment-btn`
- 固定短枚举：`.pc-select`
- 动态预设、世界书、角色、聊天、模型、工作流和资源：`SearchableCombobox`
- 数值：输入框、滑块或步进器，不使用文字按钮模拟

图标按钮必须有 `title` 和 `aria-label`。同一行常驻命令不超过 6 个；低频操作进入 `ActionMenu`。

### 6.4 表单

- 使用 `.pc-field-group`、`.pc-field-label`、`.pc-field`、`.pc-area` 和 `.pc-form-actions`。
- 标签在上、输入在下是默认形式；短数值设置可使用左标签右控件的一行布局。
- 相邻短字段允许两列，手机窄屏下必须自然回落为一列。
- 追加要求等长文本左对齐，不居中。
- 高级设置默认折叠，只保留本次任务最常改的字段。
- 表单底部提交区应稳定可达；长表单优先使用页面底部粘性操作区，但不能遮挡内容。

### 6.5 列表与目录

- 使用 `.pc-directory-toolbar`、`.pc-directory-list` 和 `.pc-list-row`。
- 整行负责进入详情，右侧只保留状态、数量或少量命令。
- 标题单行省略，必要元数据最多两行。
- 排序状态必须持久化；进入详情再返回时恢复滚动位置。
- 大量标签或类型使用搜索、筛选和最近使用，不无限增高容器。
- 空列表使用 `EmptyState`，不要同时显示数量 0、空卡和第二段空提示。

### 6.6 生成与预览

- 生成表单优先使用 `GenerationPanel` 或 `GenerationFormPage`。
- 预览优先使用 `GenerationPreviewPanel`。
- 引用统一使用 `ReferencePicker`。
- 八股检测统一使用 `BaguScanPanel`。
- 失败输出必须保留为可重新解析草稿。
- 生成离开当前页面后，完成状态必须进入全局任务提示或草稿中心，不能依赖原组件仍挂载。
- 业务动作和提示词职责分开。程序要做的版本保存、排序和跳转，不得追加成 AI 提示词。

### 6.7 阅读详情

- 使用 `ReaderDetailShell`、`ReaderContent`、`VersionNavigator` 和 `DetailFooter`。
- 正文宽度、字号、行高、颜色和字体只读取阅读器设置。
- 版本导航位置由设置决定，正文下方模式不强制悬浮。
- 网页渲染无法可靠捕获正文点击时，底栏可以始终显示。
- 底栏背景必须不透明并保证图标对比度。
- 目录、版本和操作按钮的显示不得改变正文容器宽度。

### 6.8 主题与响应式

- 新颜色必须使用 `--pc-*` 主题变量；业务状态色需有明确语义。
- 不新增绕过主题系统的 App 私有主题色。
- 酒馆主题不得决定手机日间模式下输入框、下拉框和正文颜色。
- 固定棋盘、工具栏、版本导航和媒体区域必须有稳定尺寸约束。
- 字号不随 viewport 宽度缩放。
- 至少验证 350x700、390x844、430x900，以及日间、夜间和酒馆深色主题组合。

### 6.9 反馈与错误

- 用户操作失败必须显示原因，不能表现为“点击没反应”。
- 防重复提交应锁定当前操作，不生成多个确认弹窗。
- 成功提示不应遮挡关键输入；自动后台动作应减少无必要弹窗。
- 加载、空状态、错误和成功是四种独立状态，不能互相伪装。

## 七、代码结构要求

当一个 App 同时包含 3 个以上页面，或单个 SFC 接近 800 行时，应检查是否拆为：

```text
App.vue                 路由协调与跨页状态
pages/*.vue             页面模板与页面事件
useXxxSession.ts        跨页会话和生命周期
generation.ts           生成配置、解析和保存契约
store.ts                持久化与领域操作
index.ts                App 能力注册
```

拆分不是目标，明确所有权才是目标。禁止：

- 把同一状态复制到根组件、页面组件和 store
- 新建第二套路由栈、主题变量或生成服务
- 用万能 composable 接收大量布尔开关
- 为兼容旧代码长期保留两个入口
- 在局部 CSS 中重写全局按钮和表单基础样式
- 用宽泛 `try/catch` 把错误变成默认值

## 八、验证门槛

每次 UI 或结构修改至少执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/check-ui-reuse.ps1
powershell -ExecutionPolicy Bypass -File scripts/check-style-guard.ps1
pnpm exec eslint <changed-files>
pnpm build
```

用户可见页面还必须运行对应的 `pnpm ui:check` 场景。结构性修改需要行为断言，不能只截图。

提交前检查：

1. 是否建立了第二事实来源。
2. 是否用 fallback 掩盖了错误。
3. 是否遗留旧分支、旧样式或死组件。
4. 是否把动态资源错误地做成普通 select。
5. 是否增加 `!important` 或高特异性根选择器。
6. 是否只验证了 390x844，遗漏窄屏、宽屏和暗色模式。
7. 是否修改了无关文件或覆盖用户已有改动。

## 九、重复缺陷防复发交付协议

本节解决的不是某一个页面的样式问题，而是“旧 App 修过的问题，在新 App 或另一个页面再次出现”的交付失控问题。它适用于新增 App、修改共享 UI、补充业务能力、修复重复缺陷和结构整改。

### 9.1 完成的定义

一次修改只有同时满足以下条件才算完成：

1. 用户要求已经拆成可逐项判断的验收项。
2. 已查明同类功能在项目中的合格参考实现与共享入口。
3. 修改落在正确的共享层或业务层，没有建立第二套实现。
4. 同类旧问题已全库搜索并处理；未处理命中项有明确理由。
5. 交互、数据、异常和响应式状态均有验证证据。
6. 已检查最终 diff，没有遗留死代码、旧入口、遮挡层、无事件按钮和局部重复样式。

`pnpm build` 成功只说明代码能够打包，不代表按钮有效、交互完整、UI 合格或需求完成。单张截图正常也不代表弹窗、滚动、返回、夜间模式和数据恢复正常。

### 9.2 编码前：先做模式审计

开始修改前必须完成以下动作：

1. 若方案经过多轮讨论或修改，先整理唯一的当前需求基线，把旧要求标记为“已替代”，不得混用不同轮次的结论。
2. 使用搜索定位同类 App、相同控件、相同事件和相同业务流程。
3. 阅读相关全局样式、共享组件、store、composable 和 App 注册能力。
4. 选定一个合格页面作为行为与视觉参考，记录需要保持的不变量。
5. 判断本次问题是局部业务差异还是共享模式缺陷。只要两个以上页面可能复发，就按共享问题处理。
6. 检查用户已有数据、旧版本字段和当前布局，避免“修新页面、破坏旧数据”。

当前需求基线至少使用以下字段：

| 编号 | 当前最终要求 | 被替代的旧要求 | 影响范围 | 合格参考 | 验证方法 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| R1 | 可直接验收的一句话 | 无或旧结论 | 文件、App、共享流程 | 现有组件或页面 | 行为、尺寸、主题、数据 | 待办/完成/未验证 |

后续用户再次调整方案时，修改这张基线，而不是另起一份互相冲突的清单。实现和最终交付只能以当前基线为准。

新增 App 不能只复制一个入口卡和空页面就视为完成。它必须先确定自己复用的页面骨架、详情骨架、生成流程、持久化边界、错误状态和导入导出契约。

### 9.3 实现中：同一规则只能有一个入口

- 视觉基础规则进入全局样式或共享组件，App 内只写独有布局。
- 同一种标签页、按钮、下拉框、弹窗和操作菜单使用相同组件、类名与尺寸变量。
- 同一种生成、解析、失败草稿、版本切换、阅读详情和目录交互必须复用共享流程。
- 修复共享缺陷时，应修改权威入口并删除局部补丁；禁止给每个 App 再加一次 CSS 覆盖或事件兜底。
- 需要业务差异时使用明确参数或插槽，不复制整个组件后各改一份。
- 用户操作失败必须进入可见错误状态；禁止空 `catch`、伪成功和静默回退。

本项目不接受“顺手兜底”：

- 不因阅读代码时发现附近问题而顺手修改无关功能。
- 不因担心接口失败而额外增加默认成功、空数据、旧接口重试或第二条事件链。
- 不以“兼容”为名长期并存新旧 store、新旧路由、新旧解析器或两套 UI。
- 不在用户未要求时顺手重排目录、统一命名、格式化无关文件或扩大重构范围。
- 全库搜索是为了确认影响范围，不等于获得修改所有命中项的授权。只修复与当前要求具有同一根因、同一不变量和同一共享入口的部分；其余仅列入报告。

如果没有兜底会导致已有用户数据不可恢复，或酒馆版本差异使功能必然不可用，应先向用户说明：主路径、回退触发条件、保留期限、失败时显示的原始错误，以及以后如何删除该回退。未得到确认前，不新增这类逻辑。

### 9.4 新 App 与改版 App 的能力清单

每个 App 都必须逐项判断下列能力。不是要求所有 App 强行拥有全部功能，而是要求明确判断“需要”或“不适用”，不能漏掉：

| 领域 | 必须检查的项目 |
| --- | --- |
| 导航 | 入口、返回、关闭、页面刷新后恢复、从详情返回原列表位置 |
| 对象操作 | 新建、查看、编辑、删除或解除、批量操作、确认与撤销可能性 |
| 数据 | 作用域、持久化、改名、聊天/角色切换、空数据、旧数据兼容 |
| 安全 | 导入、导出、覆盖策略、备份、失败后原始数据是否仍保留 |
| 生成 | 来源、预设、API、任务模板、占位符、停止、失败草稿、重新解析 |
| 阅读 | 标题、正文、目录、滚动位置、版本、思维链、网页内容、字体和夜间模式 |
| 反馈 | 加载、成功、空状态、禁用、错误原因、长任务进度、重复点击保护 |
| UI | 350px 窄屏、长标题、长选项、两位数以上计数、键盘弹出、弹窗遮挡 |
| 无障碍 | 图标按钮的 `title`、`aria-label`、可点击范围、文字与背景对比度 |

### 9.5 已知高频复发问题清单

后续新增或改动相关页面时，必须针对下列问题做回归检查：

1. 按钮显示出来但没有绑定事件、事件被遮挡层截获，或点击后没有任何反馈。
2. 开关点击区域与小问号、标签或弹窗事件冒泡混在一起，导致点击开关却打开说明。
3. 标签页、按钮、标题和下拉框在不同 App 中自行放大，窄屏出现挤压、换行或裁切。
4. 同一阅读详情在某类内容中缺少目录、版本、来源楼层、思维链、字体或底部操作。
5. 新增分组后只能创建，不能删除、解除、改名或移动。
6. 解析失败后原始输出丢失，不能编辑并重新解析，或不知道具体哪一段失败。
7. 生成页遗漏预设、API 配置、来源、引用或类型提示词，批量生成与单次生成能力不一致。
8. 用户设置被页面初始化值覆盖，例如楼层固定重新变成 `20`，而不是记住上次输入。
9. 动态下拉框过长被容器截断，或使用不可搜索的原生下拉框。
10. 仅正常数据状态可用；加载、空、失败、禁用、夜间模式或返回恢复状态未经实现。
11. 只修截图所示页面，没有搜索其他同类按钮、详情页、生成页和设置项。
12. 用新增局部 CSS 修正尺寸，导致下一 App 再次复制同样问题。

用户再次报告上述任一问题时，修复流程必须包含：全库搜索同类模式、列出命中位置、确认共同根因、修复共享入口、清理属于同一根因的局部补丁、增加回归验证。不同根因或无关功能只报告，不顺手修改。若确实只能局部修改，交付说明必须写明为什么不会在其他页面复发。

代码审计、UI 检查和“辛辣评价”不属于修复证据。审计中发现的每个有效问题都必须转换成：缺陷编号、复现位置、共同根因、影响范围、修复入口和回归场景。没有进入该闭环的问题只能称为“已发现”，不能称为“已处理”。

### 9.6 强制验收矩阵

用户可见改动至少按以下矩阵验证：

| 类别 | 最低验证 |
| --- | --- |
| 静态 | TypeScript、ESLint、UI 复用检查、样式守卫、构建 |
| 行为 | 每个新增或修改按钮至少实际触发一次；失败路径至少验证一次 |
| 状态 | 加载、空、正常、错误、禁用；涉及持久化时刷新或重进验证 |
| 尺寸 | `350x700`、`390x844`、`430x900` |
| 主题 | 日间、夜间；涉及输入框和弹窗时检查酒馆深色主题污染 |
| 导航 | 进入、返回、关闭、详情返回原页面、滚动或选中状态保持 |
| 数据 | 新建、修改、删除/解除；涉及文件时导入导出和失败不丢数据 |

视觉场景必须包含真实操作断言，不能只截首屏。点击测试应确认目标状态真的改变，而不是只确认元素存在。

### 9.7 交付记录格式

每次较大修改的最终说明必须明确列出：

1. 本次验收项及其状态：已完成、未完成、未验证或不适用。
2. 采用的共享组件/权威入口，以及删除了哪些旧实现。
3. 全库同类问题的搜索范围、命中数量和处理结果。
4. 实际运行的检查、交互场景、尺寸和主题。
5. 仍存在的限制与原因。

禁止使用“应该没问题”“顺便检查了其他页面”“基本完成”这类无法核验的表述。没有证据的内容必须标为未验证。

## 十、代码与 UI 防复发完整整改方案

方案建立日期：2026-08-13

本方案不讨论 App 分类，也不新增业务功能。目标是把现有规范变成可以执行、可以阻止回归、可以逐批交付的工程流程，解决以下核心问题：同一种 UI 在不同 App 中反复走样；修过的交互在新 App 中再次失效；页面只实现正常状态；审计只指出问题却没有转成修复与测试；方案多次修改后新旧要求混用。

当前实施基线：`src` 下约有 185 个 Vue 文件，其中 23 个超过 800 行、14 个超过 1200 行；`src/apps` 有 30 个 App 目录；`PhoneOverlay.vue` 约 2002 行；`visual-harness.ts` 约 3776 行。项目已有共享 UI、生成管线、阅读详情和视觉测试，整改重点是收紧唯一入口和交付门槛，不是重新写一套框架。

### 10.1 唯一需求基线

以下表格是本轮整改的唯一需求基线。后续修改要求时直接更新本表，被替代内容标为失效，不另建并行方案。

| 编号 | 当前最终要求 | 影响范围 | 验收标准 |
| --- | --- | --- | --- |
| Q1 | 修过的代码和 UI 问题不得在新 App 或同类页面中重复出现 | 全部共享控件与 App | 同一问题有唯一实现和回归场景 |
| Q2 | 新建或改版 App 必须先复用合格页面、全局类和共享流程 | Vue 页面、全局 CSS、共享组件 | 不新增重复基础控件和第二套流程 |
| Q3 | 所有可见操作必须真实可用，不能出现按钮无反应、遮挡或错误事件冒泡 | 按钮、开关、弹窗、菜单、拖拽 | 实际点击后状态与数据正确改变 |
| Q4 | 解析、生成和文件操作失败必须保留原始内容并允许恢复或重试 | 生成、解析、导入导出、备份 | 错误可定位，原始数据不丢失 |
| Q5 | 相同阅读、生成、设置和对象管理能力在不同 App 中保持一致 | 共享业务流程及其消费者 | 能力矩阵逐项通过或明确不适用 |
| Q6 | UI 使用统一密度、字号、控件高度和响应式规则 | 全部手机页面 | 三种尺寸和日夜主题均通过 |
| Q7 | 不顺手修改无关问题，不新增“以防万一”的兜底 | 全仓库 | diff 仅含当前同一根因范围 |
| Q8 | 不能以构建成功、单张截图或文字审计代替完成证据 | 测试与交付 | 验收表含行为、状态、尺寸和数据证据 |

### 10.2 整改范围与明确不做事项

本轮包含：

- 全局按钮、图标按钮、标签页、字段、弹窗、菜单、列表和详情页的视觉与行为契约。
- 生成、失败草稿、重新解析、阅读详情、目录、版本、思维链和句子编辑等共享流程。
- App 的导航、增删改查、导入导出、错误反馈、状态持久化和作用域切换检查。
- `PhoneOverlay`、视觉测试协调器及高风险根 App 的职责拆分。
- 防止重复样式、无事件按钮、缺少回归场景和测试端口残留的自动守卫。

本轮不包含：

- App 重新分组、首页分类和教程分类调整。
- 用户没有提出的新业务功能、顺手优化、统一改名和无关目录搬迁。
- 为了“更保险”新增默认成功、静默回退、第二套 store、第二套路由或兼容分支。
- 一次性重写所有 App 或一次性移动所有旧目录。
- 与当前缺陷没有同一根因的审计发现；这些只记录，不修改。

### 10.3 目标架构与不可破坏的不变量

整改完成后必须保持以下结构：

```text
global.css / shared components
  └─ 统一视觉尺寸、主题、基础交互和无障碍语义

core / composables / stores
  └─ 生成、阅读、路由、作用域、持久化和错误处理的唯一业务入口

App root
  └─ 只协调页面、路由参数和跨页会话

pages
  └─ 只渲染当前页面并调用共享能力

tests / visual scenarios
  └─ 验证共享不变量和每个 App 的业务差异
```

不可破坏的不变量：

1. settings store 是界面、阅读器和连接设置的唯一状态来源。
2. `useChatScopedDomain` 是聊天作用域数据的统一边界。
3. generation service 与 adapter 是提示词组装和生成请求的唯一主路径。
4. `ReaderDetailShell` 是内容阅读详情的统一骨架。
5. App registry 是跨 App 能力的唯一注册入口。
6. 用户已有布局、当前聊天数据和导入内容不得因纯 UI 整改发生迁移或重置。
7. 每次只替换一个权威入口；新入口启用后删除同批次旧实现，不长期并存。

### 10.4 阶段 0：冻结基线并建立缺陷台账

本阶段不修改业务行为。

工作内容：

1. 为每项用户要求建立编号、复现位置、共同根因、影响文件、合格参考和验收场景。
2. 保存当前三种尺寸的全量 UI 报告，并记录已有失败与警告，避免把旧问题误判为本次回归。
3. 记录所有超过 800 行的协调组件、局部基础控件覆盖、原生动态下拉和裸 `catch`，只做分类，不顺手整改。
4. 对现有用户数据执行只读契约检查，确认备份、聊天作用域和设置 schema 基线。

交付物：唯一需求基线、缺陷台账、影响范围清单和实施批次表。

通过条件：每个准备修改的问题都能回答“复现在哪里、共同根因是什么、修改哪个唯一入口、如何验证”。

### 10.5 阶段 1：先补质量门槛

在批量改 UI 前先增强守卫，否则旧问题会继续进入新代码。

目标文件：

- `scripts/check-ui-reuse.ps1`
- `scripts/check-style-guard.ps1`
- `scripts/ui-visual-check.mjs`
- `src/testing/visual-harness.ts`
- `src/testing/visual/*.ts`
- `package.json`

工作内容：

1. UI 复用检查增加以下规则：App 内重写基础控件尺寸、硬编码非业务颜色、图标按钮缺少名称、明显无事件按钮、重复标签页基础样式。
2. 样式守卫继续禁止 App 内 `!important`，并把新增高特异性选择器和基础控件覆盖作为失败。
3. 视觉检查默认尺寸改为 `350x700`、`390x844`、`430x900`，自动选择可用端口并保证异常退出后关闭 preview server。
4. 视觉场景从“元素存在”升级为“操作后状态改变”，优先覆盖关闭弹窗、开关、删除/解除、返回、目录、重新解析和设置持久化。
5. 把继续膨胀的 `visual-harness.ts` 按业务域拆出场景行为，主文件只负责注册、fixture 和运行。
6. 在 `pnpm verify` 中固定执行严格 UI 复用检查；遗留问题使用有编号的临时清单，新增问题不得进入清单。

通过条件：故意加入一个无事件按钮、局部基础按钮尺寸或无法关闭的弹窗时，至少一个自动检查会失败；视觉检查连续运行不会再因固定端口残留而卡住。

### 10.6 阶段 2：统一全局 UI 密度与控件语义

先修全局入口，再移除 App 局部覆盖。不要逐 App 重新调一次字号。

目标文件：

- `src/global.css`
- `src/components/ActionMenu.vue`
- `src/components/SearchableCombobox.vue`
- `src/components/CatalogModal.vue`
- `src/components/InfoHint.vue`
- 仅在确认三个以上页面存在同一结构时新增共享组件

统一规格：

| 项目 | 统一规格 |
| --- | --- |
| 正文 | 14px，正常行高，不随 viewport 缩放 |
| 辅助文字 | 12px；不影响决策的灰字直接删除 |
| 小节标题 | 16px；App 名称仍由顶栏提供 |
| 普通文字按钮 | 34px 高、13px 字号 |
| 紧凑按钮 | 30px 高、12px 至 13px 字号 |
| 图标按钮 | 34px × 34px，必须有 `title` 和 `aria-label` |
| 标签页按钮 | 32px 高、13px 字号、单行；容器不允许换行挤压 |
| 输入框与下拉框 | 最小 40px 高；长选项使用可搜索下拉 |
| 页面间距 | 主间距 12px，小间距 6px 至 8px，不使用大空白制造层级 |
| 首页五列名称 | 单行显示，至少容纳 5 个中文字，超出后省略 |

工作内容：

1. 把尺寸与字号变成全局变量和全局类规则，禁止 App 通过 scoped CSS 改写基础尺寸。
2. 标签页统一使用 `.pc-segment` 与 `.pc-segment-btn`；只允许业务布局控制宽度，不允许自行改变字体和高度。
3. 常驻高频操作使用文字或清晰图标；低频操作进入 `ActionMenu`，同一行不堆叠大量按钮。
4. 动态预设、角色、世界书、聊天、模型和资源统一使用 `SearchableCombobox`。
5. 弹窗统一处理遮罩点击、关闭按钮、滚动锁定、层级、键盘和窄屏高度。
6. 删除重复标题、重复空状态、无意义符号和不影响用户决策的灰色说明。

通过条件：相同控件在任意 App 中的计算高度和字号一致；350px 宽度下标签页不换行、按钮不互相覆盖、长选项不被容器裁切；日夜模式下文字和按钮均可辨认。

### 10.7 阶段 3：统一共享行为契约

#### 生成契约

所有生成 App 必须通过 `GenerationPanel`、`GenerationProviderFields`、`GenerationSourceFields`、`ReferencePicker` 和 generation adapter 组合，不得各自遗漏预设、API、来源或引用。

最低能力：单次与批量均可选择允许的预设和 API；停止生成；保留原始输出；解析失败显示具体原因；修改原始输出后重新解析；离开页面后任务状态可恢复；成功保存与预览模式遵循统一设置。

#### 阅读契约

日记、总结、番外、小剧场、论坛、书信、阅读聊天和剧情梳理等详情统一使用 `ReaderDetailShell`。业务页面只提供标题、正文、目录数据、版本数据和允许的动作。

最低能力：滚动标题、正文、目录、上一项/下一项、置顶/置底、版本位置不跳动、阅读器字体、夜间模式、思维链折叠、句子编辑、来源信息和网页正文点击行为。某类内容不适用的能力必须在验收表注明。

#### 对象管理契约

存在可持久化对象的 App 必须判断：新建、查看、编辑、删除或解除、批量选择、导入、导出、改名和作用域切换。删除与解除必须区分；危险操作必须明确目标，不提供静默撤销假象。

#### 设置契约

开关本体、标签和小问号必须是独立事件区域；点击开关只改变设置，点击说明只打开说明。设置保存后重进仍保持，初始化不得把用户值重新写成默认值。

通过条件：每个共享契约至少有一组组件级或单元行为测试，并在两个以上实际 App 场景中验证；业务页面不再复制主流程。

### 10.8 阶段 4：按风险顺序收口所有 App

每一批只处理同一共享不变量，完成并验证后再进入下一批。

#### A 批：全局壳与设置

- `PhoneOverlay`
- 设置
- 主题
- 首页、Dock、文件夹、顶栏和全局提示

重点：路由、返回、拖拽、弹窗层级、主题变量、字体、控件尺寸和设置持久化。

#### B 批：生成与阅读内容

- 总结、日记、番外、小剧场、论坛、书信
- 阅读聊天、剧情梳理、写卡工坊

重点：生成配置一致、失败草稿、重新解析、阅读详情、目录、版本、思维链、来源和句子编辑。

#### C 批：数据与酒馆配置

- 聊天档案、酒馆备份管理、插件文件仓库
- 资料表、关系网、时间确认、世界书槽位、世界书联动、条目库
- 提示词、预设管理、预设绑定、正则替换、正则向导

重点：作用域、改名、删除/解除、导入导出、错误可见、蓝绿灯语义、设置与数据不串联。

#### D 批：加工与媒体

- 八股去除、内容转换、楼层插入、工作台、App 工坊、MVU 修改器
- ComfyUI、媒体生成、云媒体、相册、音乐、视频和小游戏

重点：动态资源选择、长表单密度、批量操作、任务状态、媒体加载失败和特殊布局不污染全局控件。

单个 App 的通过条件：能力清单全部标为已验证或不适用；新增/修改操作有实际点击断言；350、390、430 三个尺寸无横向溢出；日夜模式可读；没有新增基础控件局部样式；刷新或重进后应持久化的状态仍存在。

如果某批目标文件职责过重，必须先为该批相关行为建立回归场景，再执行 10.9 的无行为结构拆分，然后才修改业务表现。不能先在巨型根组件中完成一遍功能修改，最后再整体拆分一次。

### 10.9 阶段 5：拆分高风险协调器

结构拆分必须在行为契约和回归场景稳定后进行，拆分批次不得同时改变业务表现。

优先顺序：

1. `PhoneOverlay.vue`：拆出首页布局与拖拽、文件夹弹窗、窗口位置、toast 桥接、路由滚动恢复；根组件只保留手机壳、顶栏和当前 App 装载。
2. `ReaderApp.vue`：拆出聊天选择、只读详情、目录和文本编辑会话。
3. `RecoveryApp.vue` 与 `ChatArchiveApp.vue`：按入口、扫描、列表、详情、导入导出和删除会话拆分。
4. `CardWriterApp.vue`、`ThemeApp.vue`、`DiaryApp.vue`、`PromptsApp.vue`：按现有页面状态拆出页面组件和 composable。
5. 其他超过 1200 行的根 App：只有在职责确实混杂时拆分，不按行数机械切割。

结构目标：根 App 尽量低于 800 行；单个页面或 composable 只拥有一个主要职责；跨页数据仍由现有 store 或明确会话 composable 管理；不复制状态；旧分支在同批次删除。

通过条件：拆分前后的行为场景、持久化数据和截图结果一致；没有新增转发组件、第二路由或双写状态。

### 10.10 阶段 6：全量回归与交付

每个批次执行针对性验证，全部批次完成后执行全量验证：

```powershell
pnpm test:unit
pnpm test:contracts
pnpm lint
pnpm typecheck
pnpm style:check
powershell -ExecutionPolicy Bypass -File scripts/check-ui-reuse.ps1 -Strict
pnpm ui:check -- --sizes=350x700,390x844,430x900
pnpm build
```

涉及酒馆运行时 API、提示词组装、预设、世界书、聊天文件或 iframe 的修改，还必须按第十一节的数据隔离和授权规则，在实际酒馆页面执行真实操作，不能只使用视觉 harness。实际操作前后保存捕获结果或数据差异，证明请求、保存和恢复路径正确。

最终交付必须包含：

- 当前需求基线逐项状态。
- 每批修改的共享入口、消费者和删除的旧实现。
- 全库搜索命中数量及未修改项原因。
- 单元、契约、静态、视觉和实际酒馆验证结果。
- 未完成、未验证和不适用项目，不使用模糊措辞。

### 10.11 批次边界、数据安全与停止条件

批次规则：

1. 一个批次只解决一个共享不变量或一个紧密业务域。
2. UI 尺寸统一与业务逻辑重写分开；纯结构拆分与行为改变分开。
3. 每批结束时代码必须可构建、可运行、可单独回退。
4. `dist` 只在源代码验证全部通过后重建。
5. 不格式化无关文件，不覆盖用户已有工作树修改。

数据规则：

- 纯 UI 整改不得修改 schema。
- 必须迁移数据时使用显式版本、事务式导入和迁移前导出，不用静默兼容分支。
- 删除、覆盖、改名和批量处理必须先解析明确目标；失败时保留原始数据和错误。

出现以下情况必须停止当前批次并报告，不能自行兜底：

- 当前要求与旧数据行为冲突，且无法从现有文档确定最终语义。
- 修复需要扩大到不同根因或用户未授权的功能。
- 无法稳定复现按钮、解析、作用域或数据丢失问题。
- 必须执行不可逆数据迁移或真实文件覆盖。
- 共享组件无法覆盖业务差异，除非改变公共 API 或建立第二套流程。
- 基线测试已经失败，无法判断失败是旧问题还是本次回归。

### 10.12 推荐实施顺序

实际开始修改时严格按以下顺序：

```text
阶段 0 基线与台账
  → 阶段 1 自动守卫
  → 阶段 2 全局 UI 尺寸与语义
  → 阶段 3 生成/阅读/对象/设置契约
  → 阶段 4 按 A、B、C、D 批循环执行：先补测试，需要时做无行为拆分，再修业务
  → 阶段 5 只处理仍未随业务批次拆分的纯结构债务
  → 阶段 6 全量与真实酒馆回归
```

不能跳过阶段 1 直接批量改页面，也不能在阶段 2 顺手增加业务功能。某个阶段发现的新问题先进入台账；只有它与当前批次同一根因时才纳入当前修改。

## 十一、自动执行协议

本协议适用于用户要求“自动进行”“按方案继续”“完成全部阶段”或一次任务需要连续执行两个以上批次的情况。它解决的是无人持续盯守时的权限、范围、数据安全和完成判断问题。第十节决定做什么，本节决定每一步在什么条件下可以自动做、什么时候必须停止。

### 11.1 启动条件与优先级

自动执行开始前必须同时满足：

1. 第 10.1 节的当前需求基线没有互相冲突的条目。
2. 已完成工作树归属登记，能够区分执行前已有修改和本批修改。
3. 当前批次有书面批次契约，不以整份方案作为一个无限范围任务。
4. 当前批次的复现、验证方式和敏感操作等级已经确定。
5. 没有需要用户先决定的数据语义、兼容策略或不可逆操作。

未满足任一条件时，只允许继续只读检查和整理记录，不允许修改业务代码。若本协议与宽泛的“顺手完善”“附近一起处理”等要求冲突，以本协议的范围限制为准。

### 11.2 工作树归属协议

首次写入前记录 `git status --short`、目标文件现有 diff 和未跟踪文件，并建立归属表：

| 文件或目录 | 执行前状态 | 归属 | 本批是否允许修改 | 保护说明 |
| --- | --- | --- | --- | --- |
| 路径 | 已修改/未跟踪/干净 | 用户既有/此前任务/本批新建 | 是/否/仅指定区域 | 不能覆盖的行为或数据 |

执行规则：

- 执行前已经修改或未跟踪的内容默认属于用户或此前任务，不得覆盖、删除、重置或重新格式化。
- 当前批次必须修改一个已有 diff 的文件时，先阅读完整相关 diff，确认新增修改不会抹掉原行为。
- 无法判断同一代码区域属于谁，或修改会覆盖未完成逻辑时，立即停止并报告冲突位置。
- 禁止使用 `git reset --hard`、`git checkout --`、批量还原、全仓格式化和清理未跟踪文件。
- 未经用户明确授权，不自动执行 `git add`、commit、rebase、merge、push 或发布。

### 11.3 缺陷台账与批次契约

审计发现先进入缺陷台账，不能直接变成修改授权：

| 缺陷编号 | 可复现问题 | 共同根因 | 影响范围 | 当前状态 | 回归场景 |
| --- | --- | --- | --- | --- | --- |
| D-域-序号 | 用户能观察到的现象 | 权威入口或状态所有权问题 | 已确认文件 | 已发现/处理中/已验证 | 测试或场景 ID |

每个自动执行批次必须建立以下契约：

| 字段 | 必填内容 |
| --- | --- |
| 批次编号 | 例如 `E01`、`U02`、`GEN01` |
| 目标 | 一个可验收结果，不能写“全面优化” |
| 对应要求/缺陷 | Q 编号和 D 编号 |
| 共同根因 | 本批唯一要修复的不变量 |
| 合格参考 | 复用的组件、页面或测试 |
| 允许修改 | 明确文件或目录及原因 |
| 排除范围 | 同次搜索中不能顺手修改的内容 |
| 数据影响 | 无、测试数据、设置、聊天数据或文件 |
| 验证 | 针对性测试、UI 场景、尺寸和主题 |
| 停止条件 | 本批特有的冲突、失败或授权边界 |

一个批次只允许一个共同根因。搜索到相似外观但根因不同的问题，新增缺陷编号并留待后续，不加入当前 diff。

### 11.4 自动操作权限分级

#### A 级：可自动执行

- 读取、搜索、统计、查看 diff 和运行非破坏性诊断。
- 在批次契约允许的文件内进行可回退的源代码和测试修改。
- 运行本地 lint、类型检查、单元测试、契约检查、视觉 harness 和构建。
- 在 `tmp` 或测试 fixture 中创建有明确前缀的临时数据。
- 当前批次源代码验证通过后重建 `dist`；`dist` 必须与该批源代码一起记录。

#### B 级：满足隔离条件后可自动执行

- 浏览器操作：只能使用视觉 harness、专用测试角色、专用测试聊天或用户明确指定的测试范围。
- 新建、编辑和删除数据：只能操作本批自动创建并带测试标识的数据。
- 设置切换：只能在可恢复的测试配置中进行，并在测试后恢复测试前快照。
- 失败路径：优先使用 mock、fixture 或测试 adapter，不通过破坏真实数据制造失败。

隔离条件无法确认时，B 级自动降为 C 级。

#### C 级：必须停止并请求用户授权

- 删除、覆盖、改名、导入或恢复用户真实聊天、备份、设置快照和仓库文件。
- 在用户当前正式角色卡或聊天中插入、删除或改写楼层。
- 切换用户正在使用的酒馆预设、世界书、API 配置或全局设置。
- 发起可能计费、消耗额度或把内容发往外部服务的真实生成请求。
- 安装依赖、访问网络、改变 schema、执行数据迁移或新增兼容回退。
- Git 提交、历史改写、推送、发布和任何不可逆文件操作。
- 修改范围必须扩大到不同根因、不同业务域或批次契约外文件。

### 11.5 测试数据隔离协议

1. 测试数据使用统一前缀，例如 `__pc_test__`，并记录创建位置和唯一 ID。
2. 删除测试只删除本批创建且 ID 完全匹配的对象；来源不明的数据一律不删除。
3. 聊天相关测试优先使用 fixture；必须进入实际酒馆时使用专用测试角色和测试聊天。
4. 备份恢复、楼层插入、批量删除、设置恢复和文件仓库导入不得在正式数据上自动测试。
5. 外部 API 默认使用 mock 或本地捕获服务；真实 API 请求属于 C 级。
6. 测试结束后只清理本批创建的临时对象；无法确认归属的对象保留并报告。

### 11.6 单批自动执行循环

每个批次严格按以下顺序进行：

```text
登记批次契约与工作树归属
  → 复现问题并保存失败证据
  → 先增加会失败的针对性测试或视觉场景
  → 确认唯一共享入口和消费者
  → 必要时执行无行为结构拆分
  → 实现当前根因修复
  → 全库搜索同一根因并只处理授权命中项
  → 运行分层验证
  → 检查 diff、数据影响和旧实现清理
  → 更新台账与证据
  → 判断自动继续或停止
```

无法先写自动测试时，必须记录原因并提供可重复的人工验证步骤；不能用“页面看起来正常”替代。

### 11.7 分层验证协议

#### T0：修改点验证

修改过程中执行最快的针对性单元测试、单文件 lint 或单场景 UI 检查。T0 失败时不扩大修改范围。

#### T1：批次验证

批次结束前执行：受影响测试、类型检查、相关契约检查、严格 UI 复用检查、样式守卫、构建，以及当前批次在 `350x700`、`390x844`、`430x900` 的场景。

#### T2：阶段验证

一个阶段或 A/B/C/D 批完成后执行全量 `pnpm verify`、全量 UI 场景和已声明的日夜主题场景。全量视觉场景不要求每个页面机械乘以所有主题，而要求所有共享控件和当前修改页面至少各有日夜覆盖。

#### T3：实际酒馆验证

只在涉及运行时桥接、真实提示词组装、酒馆预设、世界书、聊天文件或 iframe 时执行，并遵守 11.4 和 11.5。T3 必须记录测试角色、测试聊天、操作前快照、实际请求或数据差异和恢复结果。

当前视觉检查工具没有提供全场景主题矩阵时，不得声称“全部日夜模式已验证”；只能报告实际运行的主题场景。

### 11.8 遗留基线与自动守卫协议

- 首次运行记录现有警告和失败，区分遗留问题与本批新增问题。
- 守卫尚未支持增量判断时，不能简单切换为全库严格失败并让所有后续工作停摆；应先实现可复现的基线比较。
- 每个批次必须做到新增警告为零、原有警告不增加；本批触及的同根因遗留项应清零。
- `ui-reuse-allow` 只能用于明确的业务特殊布局，必须带缺陷或设计编号和原因；不得用它绕过普通按钮、标签页或字段规则。
- 静态规则只能报告可由语法可靠判断的问题。按钮事件、父级委托、插槽和表单行为优先由组件测试或浏览器场景验证，禁止用脆弱正则直接判死。

### 11.9 UI 批次协议

全局 UI 修改必须先选择一组标准参考页面，至少包括：首页窄屏、普通列表、长表单、设置标签页、阅读详情、弹窗和特殊布局。先保存修改前截图，再修改全局变量或共享组件。

执行要求：

1. 全局尺寸一次只调整一类控件，例如先按钮，再标签页，再字段，不在同一批同时改完全部控件。
2. 修改全局规则前列出所有消费者；修改后优先检查标准参考页面和受影响的特殊布局。
3. App 局部布局确实需要特殊尺寸时，说明业务原因并限制选择器范围；不能重新定义基础类。
4. 无意义灰字、重复标题和空状态属于内容审计，必须有明确命中清单，不能靠自动删除文本。
5. 视觉通过必须同时满足几何、可读性和真实操作，不以截图相似度单独判断。

### 11.10 结构拆分协议

- 行数只用于发现风险，不作为拆分完成指标。
- 拆分前必须已有覆盖当前行为的测试；没有测试时先补测试。
- 无行为拆分与功能修复分成两个连续步骤，各自验证 diff。
- 状态所有权不能因拆分复制；根组件、页面和 store 之间只保留一个可写来源。
- 拆分后删除旧分支，不保留长期转发层和双写逻辑。
- 一个热点应采用“测试 → 无行为拆分 → 功能修复 → 回归”的局部循环，不等所有 App 修改完再统一拆一次。

### 11.11 自动继续与强制停止

只有同时满足以下条件才能自动进入下一批：

- 当前批次所有必需测试通过。
- diff 只包含批次契约允许的文件和同一根因修改。
- 没有新增警告、静默错误、兼容回退和第二事实来源。
- 没有触及 C 级操作或用户真实数据。
- 台账、验证证据和未处理命中项已经更新。

出现以下任一情况必须停止：

- 复现结果与方案假设不一致。
- 目标文件已有改动与本批发生不可区分的重叠。
- 同一外观问题实际来自不同根因。
- 测试基线不稳定、端口或环境残留导致结果无法复现。
- 需要新增依赖、公共 API、schema、兼容分支或第二套状态。
- 需要操作用户正式数据、真实外部 API 或执行不可逆动作。
- 连续三次修复尝试仍由同一原因失败。

停止时必须报告已经完成的安全部分、阻塞证据、未执行的操作和需要用户决定的唯一问题，不能用兜底绕过。

### 11.12 自动执行状态与完成证明

当前执行记录统一维护在 `docs/execution/`：`00` 是工作树归属，`01` 是缺陷台账，`02` 是批次状态，`03` 是 Q→D→批次→权威入口→验证证据的追踪与能力矩阵。模板与记录冲突时先停止并更新记录，不得凭聊天记忆继续。

协议执行期间维护状态表：

| 批次 | 目标 | 状态 | 修改范围 | 验证结果 | 是否可自动继续 |
| --- | --- | --- | --- | --- | --- |
| 编号 | 一句话结果 | 待办/进行中/完成/阻塞 | 文件或目录 | T0/T1/T2/T3 | 是/否及原因 |

每个批次结束后进行一次用户可见的简短进度更新；全部完成前不使用“整体完成”。最终交付必须能够从 Q 编号追溯到缺陷、批次、代码位置和测试证据。

## 十二、当前结论

项目已经具备可持续复用的骨架，尤其是 App 注册、聊天作用域、生成 adapter、引用、内容转换和基础 UI 控件。当前主要债务不再是“没有组件”，而是共享组件之上的协调层过重、主题隔离脆弱、动态下拉迁移不完整、错误仍可能被吞掉，以及视觉测试缺少语义门槛。

后续修改应围绕一个原则：先把已有能力变成唯一入口，再删除旧实现。不要再新增迁移方案文档；新的事实、约束和审计结果直接更新本文。
