# 15-仓库整理与发布收口方案

## 一、方案定位

本方案只处理仓库边界、成果归档、发布完整性、目录职责和超大文件拆分，不新增产品功能，不调整 UI，不修改聊天、世界书、预设等业务语义。

执行遵守 `07-当前代码与UI复用审计及设计要求.md`，尤其是第九节防复发要求和第十一节自动执行协议。每个实施批次都必须先登记工作树归属、单一根因、允许范围、停止条件和验证证据。

当前最重要的原则是：**先把已经验证过的功能成果形成可复现的发布候选，再整理目录。禁止在当前累计工作树上直接批量移动源码。**

## 三、目标仓库状态

整理完成后应满足：

- 当前功能成果、测试、方案和正式产物属于同一个可复现候选树。
- 安全发布不会遗漏任何必要的新文件，也不会把本地参考资料、备份或临时证据带入仓库。
- 根目录只保留构建入口、项目配置、正式源码、正式文档和明确需要跟踪的生成产物。
- `docs/` 有唯一入口，明确区分长期规范、当前方案、执行状态和历史证据。
- `src/components/` 只承担跨业务共享 UI；业务 App 最终按域归入 `src/apps/<domain>/`。
- 超大文件按真实职责拆分，拆分前后公共 API 和行为不变，不保留两套实现或长期兼容转发层。
- 完整验证、三尺寸交互、正式构建和发布候选核对可以由明确命令复现。

## 四、明确不做

本方案不允许顺手处理以下内容：

- 新功能、UI 美化、交互调整、文案调整或业务缺陷。
- 持久化 schema、完整备份格式、共享公共 API 或兼容语义变更。
- 删除真实酒馆数据、备份文件、用户预设、聊天或世界书。
- 把本地参考资料移动到另一个未知位置后再删除原目录。
- 在没有独立检查点时批量重命名全部 App、测试和文档。
- 自动提交、推送、改写 Git 历史或发布。

## 五、推荐执行顺序

### REPO00：成果冻结与候选清单

目标：证明当前 147 项改动各自属于哪个已完成批次，并生成机器可读的候选清单。

操作：

1. 记录 HEAD、index、所有已跟踪修改和全部未跟踪文件。
2. 将 15 个新源码、19 个新契约、5 个新方案逐项映射到 `docs/execution/` 的完成批次。
3. 标记正式生成物：`dist/index.js`、`dist/index.css`、`components.d.ts`。
4. 对无法映射的文件只登记为“待确认”，不得删除或纳入发布。
5. 保存当前 429/429 静态验证、正式 dist 哈希和真实酒馆复测证据。

通过条件：147 项全部有归属；未出现“来源不明但准备一起发布”的文件。

### REPO01：发布清单与方案文档收口

目标：解决五份方案文档不会被安全推送脚本纳入的问题。

推荐做法：

1. 审核 `docs/10`—`docs/14` 的需求追踪是否均已关闭。
2. 已完成方案移动到 `docs/archive/plans/`，保留原编号和标题；仍有未完成项的方案保留在 `docs/`。
3. 新增 `docs/README.md`，列出：长期规范、当前有效方案、历史方案、执行记录、发布说明。
4. 更新所有仓库内引用，运行链接检查；不得留下指向旧路径的死链接。
5. 安全推送脚本新增明确的正式文档边界，不能靠“所有 docs 都放行”的宽泛规则。

停止条件：任一方案仍含未完成需求但执行矩阵没有对应状态；此时不归档，先校正状态。

### REPO02：本地参考资料退出发布树

目标：让 `.gitignore` 的声明与 Git 实际跟踪状态一致。

推荐做法：

1. 生成当前 161 个已跟踪参考文件清单和总哈希，不删除本地文件。
2. 检查生产源码、构建脚本、测试是否运行时依赖 `可参考拓展/`；若存在依赖，先迁移真正需要的最小正式资产并记录许可证来源。
3. 在获得单独 Git 文件删除授权后，只从 Git 跟踪中移除 `可参考拓展/`，本地目录继续由 `.gitignore` 保护。
4. 验证安全推送候选不再包含其他项目的 `dist`、source map、锁文件和开发配置。

注意：该批会表现为大量 Git 删除，虽然不删除本地资料，仍属于发布树的实质变化，必须单独授权。

### REPO03：执行文档冷热分层

目标：让“当前状态”可直接阅读，同时保留完整历史证据。

推荐结构：

```text
docs/execution/
  README.md                    # 唯一当前入口
  current/
    worktree.md                # 当前基线和保护边界
    defects.md                 # 仅未完成/阻塞项及最近关闭项
    batches.md                 # 当前批次和下一批
    traceability.md            # 当前 Q→D→批次→证据
  archive/
    2026-phase-01/...          # 只读历史切片
    2026-phase-02/...
```

迁移规则：

- 历史记录只移动，不删减证据正文。
- 当前文件通过索引链接历史，不复制同一状态到多个文件。
- 旧编号和批次 ID 保持可搜索。
- 每次切片后执行批次 ID、缺陷 ID、Markdown 相对链接三类完整性检查。
- 在新结构稳定前，不删除旧入口；迁移批次结束时一次性切换引用，禁止长期双写。

### REPO04：生成文件与临时文件政策

目标：每类文件只有一个明确归属。

建议政策：

| 类型 | 是否跟踪 | 规则 |
| --- | --- | --- |
| `dist/index.js`、`dist/index.css` | 是 | 只在正式发布批次构建；必须记录源码候选和哈希 |
| `components.d.ts` 等声明生成物 | 先审计 | 若构建/编辑器必需且稳定则跟踪；否则改为可重复生成并忽略 |
| `tmp/`、视觉截图、浏览器配置 | 否 | 保持忽略；验证结束后只清理本批明确创建的路径 |
| `backups/`、`ui-review/`、预设及参考拓展 | 否 | 本地资料，不进入发布候选 |
| 测试基线 JSON | 是 | 只能由对应场景变化更新，并有差异证据 |

该批不得为了“看起来干净”删除未知临时目录；只能清理 REPO00 清单中确认由本批创建且可重建的内容。

### REPO05：测试与视觉工具拆分

目标：先拆 6045 行的 `visual-harness.ts`，不改变场景、断言或命令入口。

建议边界：

```text
src/testing/visual/
  bootstrap/       # 酒馆运行时 mock、DOM 和全局依赖
  navigation/      # 打开 App、页面返回、尺寸与主题
  fixtures/        # 数据夹具安装与回收
  assertions/      # 交互、外观和可访问性采集
  runner/          # 场景调度、结果与截图输出
```

实施要求：

- 每批只提取一个真实职责，不改场景内容。
- 旧入口改为薄协调器；不得复制 helper 后保留两套路径。
- 每次提取前后比较场景目录数量、三尺寸执行数量和结果哈希字段。
- `scripts/unit/` 是否按域分目录另立发现批次；在确认 Node test glob、ESLint 和安全推送规则前不移动。

### REPO06：业务 App 目录统一

目标：逐域把业务根组件从 `src/components/` 归入 `src/apps/<domain>/`，共享组件继续留在 `src/components/`。

准入条件：必须先建立 App 所有权清单，至少包含注册 ID、根组件、页面、store、generation、transfer、测试和视觉场景。

迁移顺序建议：

1. 选择依赖最少的一个业务域作为样板。
2. 只移动文件和更新 import，不改组件内容、导出名称或路由语义。
3. 通过 App 注册、返回、持久状态、导入导出和三尺寸场景后，再迁移下一个域。
4. 所有消费者切换后直接删除旧路径，不保留长期 re-export 兼容层。
5. `ReaderApp`、`PhoneHome`、`PromptsApp` 等跨域或核心壳先不移动，需另立职责发现批次。

### REPO07：超大业务文件拆分

目标：在目录稳定后再拆大文件，避免“搬家”和“重构”同时发生。

优先队列：

1. `PhoneHome.vue`：桌面布局、拖拽会话、文件夹弹层、活动页分离。
2. `CardWriterApp.vue`：配置表单、序列生成、结果处理分离。
3. `PromptsApp.vue`：任务模板、类型提示词、预设入口分离。
4. `ReaderApp.vue`：阅读壳、菜单、版本导航和内容渲染分离。
5. 其他超过 1200 行的业务根组件逐项发现，不机械按行数切割。

拆分标准：一个模块必须拥有明确状态或行为边界；单纯把模板片段搬进新文件但仍读写整个父组件状态，不算完成。

### REPO08：最终候选与发布门禁

最终执行顺序：

1. `git diff --check`
2. `pnpm verify:static`
3. `pnpm build:check`
4. `pnpm verify:ui`
5. 必要时执行完整三尺寸全目录视觉比较
6. `pnpm build`
7. 核对正式 dist、候选源码、测试基线和文档清单
8. 执行安全推送脚本 `-DryRun`，确认新增文件和删除文件均与清单一致
9. 停止并请求 Git 提交/推送授权

禁止把“构建通过”当作仓库整理完成。至少还要证明：新文件没有遗漏、本地资料没有混入、历史链接可达、运行入口不变、工作树差异与候选清单一致。
