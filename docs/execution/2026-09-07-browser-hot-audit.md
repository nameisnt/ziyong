- 工作树归属：所有既有业务修改和 dist 均来自前批，保留；本批只新增 tmp 测试脚本及本报告，不修改业务代码或安装文件，不提交推送。
- 服务边界：127.0.0.1 随机端口，只读提供当前 dist；使用 TypeScript
  AST 把三个宿主 import 明确改为原酒馆绝对 URL，业务逻辑不变。不传输 API 密钥或用户数据给其他服务。
- 切换前提：没有运行中的任务、没有工作流，数据版本已为 2；保存当前聊天及相关内容快照，只用于核对和清理本批临时对象。
- 最终切换流程：使用浏览器工具的 navigate_page.initScript，在页面脚本运行前只替换 ziyong-dist 入口脚本和样式地址，然后从正常酒馆启动流程加载新版。没有旧插件实例与新版同时运行。
- 退出方式：确认临时数据清理后刷新真实页面恢复安装版，再关闭本机服务。测试仅对本地临时新版有效，不代表已经部署。

## 验收记录

### 临时加载方式

最初尝试先卸载旧 Vue/Pinia，再移除五个与旧包源码完全匹配的工作台事件监听并加载新版。仅以 HTTP 重定向处理宿主 import 是错误的：不同初始模块 URL 会产生另一份设置实例，导致新版读到空设置；世界书槽位的自动同步因此临时清空了“当前聊天”中的一个自动管理条目。

发现后停止该方式，使用切换前快照尝试回写，随后刷新并重新打开原聊天，由原有槽位数据重新同步该条目。核对结果为原 UID、标题标记、启用状态、正文匹配原槽位数据；插件保存的槽位本身没有丢失。第一次直接回写的序列化比较未通过，因此不把那次回写单独记为完整恢复成功。

最终采用启动前入口替换，并把宿主 import 改成原始绝对 URL。重新建立内容摘要基线后验证：当前聊天 3 条消息、原有 3 条正则、1 个当前聊天槽位正常读取；页面仅有一个插件根节点，样式和异步 App 块从本地服务读取。没有替换安装目录文件。

### 新确认问题 / P3

删除小剧场不会同步删除其条目正则选择记录。

- 位置：`src/store/theater.ts:254` 的 deleteEntry；`src/apps/theater/TheaterApp.vue:1267` 的删除事件链只调用条目删除。
- 验证：选过正则的临时条目删除后，`regex-display.settings.usages`
  仍保留 1 个指向该条目的 content 键。调用实际 store 删除并回读确认，UI 删除链也没有相应清理。
- 影响：不会把规则应用到其他条目，但反复删除会累积不可达配置并进入备份。
- 建议修复共享的条目/版本选择清理入口，再覆盖同根因删除路径；本轮不修改业务代码。测试产生的该键已精确清理。
